Idempotent Functions

دو مفهوم مهم در طراحی سیستم‌های مطمئن — توابعی که نتیجه پیش‌بینی‌پذیر دارند و کدی که در چند محیط یکسان اجرا می‌شود.

Idempotent Functions — توابع بی‌اثر در تکرار

یک تابع Idempotent است اگر اجرای آن چند بار، همان نتیجه‌ی یک بار اجرا را بدهد. یعنی f(f(x)) === f(x). این مفهوم در طراحی API بسیار مهم است — مخصوصاً وقتی client ممکن است یک درخواست را به دلیل timeout دوباره بفرستد.

مثال روزمره: دکمه آسانسور را چند بار فشار دهید، نتیجه فرقی ندارد — آسانسور هنوز فقط یک بار می‌آید. این idempotent است. اما اگر هر فشار یک سفارش پیتزا ثبت کند، idempotent نیست!

مثال ۱ — عملیات Idempotent و غیر‌Idempotent

idempotent-examples.js
// ✅ Idempotent — هر چند بار اجرا شود نتیجه یکسان است function setUserActive(user) { user.status = 'active'; // هر بار همین مقدار را می‌گذارد return user; } // ❌ غیر Idempotent — هر اجرا نتیجه را عوض می‌کند function incrementViews(post) { post.views += 1; // هر بار یک واحد بیشتر می‌شود return post; } // ✅ HTTP PUT باید Idempotent باشد — جایگزینی کامل // PUT /users/1 { name: "Ali" } → همیشه نام را "Ali" می‌کند // ❌ HTTP POST معمولاً Idempotent نیست // POST /orders { item: "pizza" } → هر بار یک سفارش جدید می‌سازد!

مثال ۲ — Idempotency Key در API (پرکاربرد!)

در پرداخت آنلاین، اگر کاربر دکمه «پرداخت» را دو بار بزند (یا شبکه retry کند)، نباید دو بار از کارتش کسر شود. راه‌حل: Idempotency Key — یک شناسه یکتا که client می‌فرستد و سرور با آن تشخیص می‌دهد درخواست تکراری است:

idempotency-middleware.js
const redis = require('../config/redis'); // middleware برای جلوگیری از پرداخت تکراری async function idempotencyMiddleware(request, reply) { const idempotencyKey = request.headers['idempotency-key']; if (!idempotencyKey) { return reply.code(400).send({ error: 'Idempotency-Key لازم است' }); } const cacheKey = `idempotency:${idempotencyKey}`; // آیا قبلاً این درخواست پردازش شده؟ const existingResult = await redis.get(cacheKey); if (existingResult) { // همان نتیجه قبلی را برگردان — پردازش دوباره نکن! return reply.send(JSON.parse(existingResult)); } // در request ذخیره کن تا handler بتواند بعد از پردازش، نتیجه را cache کند request.idempotencyKey = idempotencyKey; } // در route handler: async function processPayment(request, reply) { const result = await paymentService.charge(request.body); // نتیجه را برای این idempotency key ذخیره کن — 24 ساعت معتبر await redis.setex( `idempotency:${request.idempotencyKey}`, 86400, JSON.stringify(result) ); return reply.send(result); }

Isomorphic Functions — توابع دوطرفه

در دنیای functional programming، Isomorphic یعنی یک تابع که می‌تواند عملیاتش را برگشت‌پذیر انجام دهد — یک تابع تبدیل به جلو، یک تابع معکوس به عقب، و ترکیب آن‌ها برابر با حالت اولیه است. در دنیای Node.js معمولاً به Isomorphic/Universal Code هم اشاره دارد — کدی که هم در سرور و هم در client یکسان اجرا می‌شود.

مثال ۱ — Isomorphism در encode/decode

isomorphic-encode.js
// دو تابع که معکوس همدیگرند — encode(decode(x)) === x function encode(obj) { return Buffer.from(JSON.stringify(obj)).toString('base64'); } function decode(str) { return JSON.parse(Buffer.from(str, 'base64').toString()); } const original = { userId: 123, role: 'admin' }; const encoded = encode(original); const decoded = decode(encoded); console.log(JSON.stringify(original) === JSON.stringify(decoded)); // true // این الگو پایه‌ی JWT، pagination cursor، و URL-safe tokenها است

مثال ۲ — Isomorphic Code بین سرور و کلاینت

کدی که هم در Node.js و هم در مرورگر بدون تغییر کار کند — مثلاً validation rules که هم در فرم سمت کاربر و هم در API سمت سرور باید یکسان اجرا شوند:

shared/validators.js — هم در Node و هم در Browser کار می‌کند
// این فایل به هیچ Node.js API خاصی وابسته نیست // نه fs، نه process — فقط منطق خالص JS function isValidEmail(email) { return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email); } function isStrongPassword(password) { return password.length >= 8 && /[A-Z]/.test(password) && /[0-9]/.test(password); } // export به سبک CommonJS — برای Node.js if (typeof module !== 'undefined') { module.exports = { isValidEmail, isStrongPassword }; } // همین فایل با <script> در مرورگر هم کار می‌کند چون توابع global می‌شوند
💡

چرا مهم است؟ اگر validation سمت client و سرور یکی نباشد، ممکن است داده‌ای که در فرم قبول شده، در سرور رد شود — تجربه کاربری بد. کد Isomorphic این مشکل را حل می‌کند.

نکات کلیدی برای مصاحبه

  • Idempotent: اجرای چندباره همان نتیجه یک بار اجرا را دارد — f(f(x)) = f(x).
  • در HTTP: GET، PUT، DELETE باید Idempotent باشند. POST معمولاً نیست.
  • Idempotency Key در API پرداخت برای جلوگیری از تراکنش تکراری — pattern واقعی صنعتی.
  • Isomorphic در FP یعنی دو تابع معکوس هم (encode/decode). در عمل به کد مشترک client/server هم اشاره دارد.
  • کد Isomorphic باید فقط از JS خالص استفاده کند — بدون وابستگی به Node.js API مثل fs یا process.
  • سوال رایج: «چرا POST idempotent نیست ولی PUT هست؟» — POST هر بار یک منبع جدید می‌سازد (مثلاً سفارش جدید)؛ PUT یک منبع مشخص را با یک مقدار جایگزین می‌کند، پس چند بار اجرا همان نتیجه یک بار را دارد.
  • یک تله رایج: فکر کردن idempotent یعنی «بدون side effect» — اشتباه است؛ idempotent یعنی side effect بعد از اولین اجرا تکرار نمی‌شود، نه اینکه اصلاً وجود ندارد.
  • کاربرد واقعی Idempotency Key: کاربر روی دکمه پرداخت دو بار کلیک می‌کند (یا شبکه retry می‌کند) — سرور با کلید یکتا تشخیص می‌دهد این همان درخواست قبلی است و دوباره از کارت کسر نمی‌کند.
  • در طراحی API، عملیات retry-safe (idempotent) امکان استفاده امن از الگوی retry با exponential backoff را می‌دهد — بدون نگرانی از اجرای تکراری.
