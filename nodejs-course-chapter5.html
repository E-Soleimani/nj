Git
Basics

Git یک سیستم کنترل نسخه است که تمام تغییرات کد شما را ردیابی می‌کند. می‌توانید به هر نسخه قبلی برگردید، با تیم همکاری کنید، و کدهای موازی بنویسید. هیچ developer حرفه‌ای بدون Git کار نمی‌کند.

commit branch merge stash .gitignore

Git چیست و چرا لازم است؟

تصور کنید روی یک فایل کار می‌کنید و آن را خراب می‌کنید. بدون Git باید از اول بنویسید. با Git می‌توانید به نسخه دیروز برگردید. یا تصور کنید دو نفر روی یک فایل کار می‌کنند — Git می‌تواند تغییرات هر دو را ادغام کند.

تشبیه ساده: Git مثل یک ماشین زمان برای کد است. هر بار که commit می‌کنید، یک عکس از وضعیت پروژه می‌گیرد. هر وقت خواستید می‌توانید به هر عکسی برگردید.

سه ناحیه اصلی Git

برای درک Git باید بدانید فایل‌ها در کدام ناحیه هستند:

📝

Working Directory

فایل‌هایی که الان روی آن‌ها کار می‌کنید — تغییرات هنوز ثبت نشده

→
📦

Staging Area

فایل‌هایی که با git add انتخاب کرده‌اید — آماده برای commit

→
🗄️

Repository

تاریخچه کامل پروژه — همه commitها اینجا ذخیره شده‌اند

چرا Staging Area وجود دارد؟ گاهی چند فایل را تغییر می‌دهید ولی می‌خواهید فقط بخشی را commit کنید. Staging به شما کنترل می‌دهد که دقیقاً چه چیزی در commit باشد.

تنظیم اولیه Git

اول از همه، Git باید بداند شما کی هستید — این اطلاعات در هر commit ثبت می‌شود:

terminal — یک‌بار برای همیشه
# نام و ایمیل شما در همه commitها نمایش داده می‌شود git config --global user.name "Elshan Dev" git config --global user.email "elshan@example.com" # تنظیم VS Code به عنوان ویرایشگر پیش‌فرض git config --global core.editor "code --wait" # نام branch اصلی را main بگذاریم (پیش‌فرض جدید) git config --global init.defaultBranch main # مشاهده همه تنظیمات git config --list

دستورات روزانه Git

شروع پروژه و وضعیت

terminal
# شروع یک repo جدید در پوشه جاری git init # وضعیت فایل‌ها — اولین دستوری که یاد می‌گیرید git status git status -s # نسخه کوتاه‌تر # مشاهده تاریخچه commitها git log git log --oneline # یک خطی — خلاصه git log --oneline --graph # با نمودار شاخه‌ها git log --oneline -10 # فقط ۱۰ commit آخر

Staging و Commit — قلب کار روزانه

این دو دستور را هر روز استفاده می‌کنید. درکشان مهم است:

terminal
# اضافه کردن فایل به staging area git add index.js # یک فایل مشخص git add src/ # همه فایل‌های یک پوشه git add . # همه تغییرات در پوشه جاری git add -p # انتخابی — بخش به بخش می‌پرسد # commit کردن — ذخیره دائمی snapshot git commit -m "feat: add user login endpoint" # add + commit در یک دستور (فقط برای فایل‌های tracked) git commit -am "fix: resolve login redirect bug" # تغییر پیام آخرین commit (قبل از push!) git commit --amend -m "feat: add user authentication" # مشاهده تغییرات قبل از commit git diff # تغییرات unstaged git diff --staged # تغییرات staged — آنچه commit خواهد شد
💡

پیام commit خوب: از پیشوندهای استاندارد استفاده کنید: feat: قابلیت جدید، fix: رفع باگ، docs: مستندات، refactor: بهبود کد، test: تست. این قرارداد در اکثر تیم‌ها رایج است.

Branch — کار موازی

Branch یعنی یک خط موازی از تاریخچه. وقتی روی یک feature کار می‌کنید، یک branch جدید می‌سازید تا کد اصلی دست نخورد. وقتی تمام شد، merge می‌کنید.

terminal
# لیست همه branchها (ستاره = branch فعلی) git branch git branch -a # شامل remote branches # ساخت branch جدید git branch feature/user-auth # رفتن به branch git checkout feature/user-auth git switch feature/user-auth # روش مدرن‌تر # ساخت + رفتن — در یک دستور git checkout -b feature/payment git switch -c feature/payment # روش مدرن # merge — ادغام branch به main git switch main git merge feature/user-auth # حذف branch بعد از merge git branch -d feature/user-auth # ایمن — فقط اگر merge شده باشد git branch -D feature/user-auth # اجباری

Stash — ذخیره موقت تغییرات

فرض کنید نصفه‌کاره روی یک feature هستید و باید سریع branch عوض کنید. نمی‌توانید commit کنید چون کد هنوز کامل نیست. Stash تغییرات را موقتاً کنار می‌گذارد:

terminal
# ذخیره موقت تمام تغییرات git stash git stash push -m "in progress: payment form" # با توضیح # لیست stashها git stash list # stash@{0}: On main: in progress: payment form # stash@{1}: WIP on feature/login # برگرداندن آخرین stash git stash pop # برمی‌گرداند و از لیست حذف می‌کند git stash apply # برمی‌گرداند ولی در لیست نگه می‌دارد # برگرداندن یک stash خاص git stash pop stash@{1}

Undo — لغو تغییرات

مهم‌ترین مهارت در Git — دانستن اینکه چطور اشتباهات را برطرف کنید:

terminal
# خروج از staging — فایل unstaged می‌شود ولی تغییرات حفظ می‌شود git restore --staged index.js # لغو تغییرات یک فایل — به آخرین commit برمی‌گردد git restore index.js # ⚠️ این کار برگشت‌پذیر نیست — تغییرات از بین می‌رود! # revert — ایمن‌ترین روش undo # یک commit جدید می‌سازد که عکس تغییرات قبلی را دارد # تاریخچه دست نخورده باقی می‌ماند git revert HEAD # آخرین commit را undo کن git revert abc1234 # یک commit خاص را undo کن # reset — تاریخچه را تغییر می‌دهد (خطرناک بعد از push!) git reset --soft HEAD~1 # آخرین commit را undo، تغییرات staged می‌مانند git reset --hard HEAD~1 # همه چیز از بین می‌رود — با احتیاط!
⚠️

قانون طلایی: هیچ‌وقت روی commitهایی که push کرده‌اید reset --hard نکنید. تاریخچه دیگران را خراب می‌کند. برای undo ایمن همیشه از revert استفاده کنید.

فایل .gitignore

بعضی فایل‌ها نباید commit شوند: پوشه node_modules (سنگین است)، فایل .env (حاوی رمز)، فایل‌های build (می‌توان دوباره ساخت). این‌ها را در .gitignore می‌نویسید:

.gitignore — برای پروژه Node.js
# پکیج‌های npm — از package.json قابل rebuild است node_modules/ # متغیرهای محیطی — حاوی رمز و اطلاعات حساس .env .env.local .env.production .env.*.local # فایل‌های build — قابل rebuild dist/ build/ .next/ # لاگ‌ها *.log logs/ npm-debug.log* # فایل‌های سیستم‌عامل .DS_Store # MacOS Thumbs.db # Windows # تنظیمات IDE (اختیاری — بعضی‌ها prefer می‌کنند commit کنند) .vscode/settings.json .idea/

نکات کلیدی برای مصاحبه

  • git add فایل را به staging می‌برد — هنوز ذخیره دائمی نشده. git commit snapshot دائمی می‌سازد.
  • git stash برای تغییر branch بدون از دست دادن کار ناتمام — مثل bookmark.
  • revert ایمن است — تاریخچه را حفظ می‌کند. reset --hard خطرناک — تاریخچه را حذف می‌کند.
  • پیام commit باید واضح باشد: feat: add login نه fix stuff.
  • هر feature = یک branch جداگانه. کدهای نیمه‌کاره را به main merge نکنید.
  • .gitignore را اول از همه بسازید — قبل از اولین commit.
  • سه ناحیه اصلی Git: Working Directory (فایل‌هایی که ویرایش می‌کنید)، Staging Area (آماده commit)، Repository (تاریخچه ذخیره‌شده).
  • سوال رایج: «فرق git pull و git fetch چیست؟» — fetch فقط تغییرات remote را دانلود می‌کند بدون merge؛ pull هم دانلود می‌کند هم خودکار merge می‌کند (معادل fetch + merge).
  • سوال رایج: «فرق merge و rebase چیست؟» — merge یک commit جدید می‌سازد که دو branch را به هم وصل می‌کند (تاریخچه شاخه‌ای می‌ماند)؛ rebase کل commitهای یک branch را روی نوک branch دیگر می‌گذارد (تاریخچه خطی می‌شود).
  • یک تله رایج: git reset --hard روی commitهایی که push شده‌اند خطرناک است — اگر دیگران آن commit را pull کرده باشند، تاریخچه‌شان با شما ناسازگار می‌شود.
  • برای لغو آخرین commit بدون از دست دادن تغییرات: git reset --soft HEAD~1 — این تغییرات را در staging نگه می‌دارد، فقط خود commit را برمی‌گرداند.
