Testing &
TDD Basics

تست نوشتن یعنی کدی بنویسید که کد دیگرتان را چک کند. این کار باعث می‌شود هنگام تغییر کد، مطمئن باشید چیزی نشکسته. TDD یک رویکرد است که می‌گوید اول تست بنویسید، بعد کد.

Jest Unit Test TDD Mock Coverage

چرا تست بنویسیم؟

تصور کنید یک تابع ۱۰۰ خطی دارید. بعد از چند ماه باید آن را تغییر دهید. بدون تست نمی‌دانید آیا تغییرتان چیزی شکسته یا نه — باید دستی همه چیز را امتحان کنید. با تست، بعد از هر تغییر فقط دستور npm test می‌زنید و در چند ثانیه می‌دانید همه چیز درست است.

تشبیه: تست مثل دستورالعمل تست کارخانه است. قبل از اینکه ماشین از خط تولید بیاید بیرون، ۵۰۰ چک خودکار روی آن انجام می‌شود. اگر یکی fail شود، ماشین خط تولید را ترک نمی‌کند.

سه نوع تست

🔬

Unit Test

تست یک تابع یا کلاس به تنهایی — بدون database یا شبکه. سریع است و زیاد نوشته می‌شود.

🔗

Integration Test

تست چند ماژول با هم — مثلاً route + service + database. کندتر ولی واقعی‌تر.

🌐

E2E Test

تست کل سیستم از دید کاربر — مثلاً با مرورگر. کندترین ولی جامع‌ترین.

💡

قانون هرم تست: Unit test زیاد بنویسید (سریع و ارزان است). Integration test متوسط. E2E کم (کند و گران است). نسبت معمول: ۷۰٪ Unit، ۲۰٪ Integration، ۱۰٪ E2E.

TDD — Test Driven Development

TDD یک روش توسعه است که می‌گوید: اول تست بنویس، بعد کد. این عجیب به نظر می‌رسد ولی فوایدی دارد: کد شما قابل تست می‌شود، طراحی بهتر می‌شود، و coverage بالا می‌رود.

🔴

Red — تست بنویس

یک تست بنویس که fail می‌شود چون کد هنوز نوشته نشده

→
🟢

Green — کد بنویس

کمترین کد ممکن برای اینکه تست pass شود

→
🔵

Refactor — بهتر کن

کد را تمیز کن. تست باید هنوز pass باشد

نصب و راه‌اندازی Jest

Jest محبوب‌ترین testing framework برای JavaScript و Node.js است. توسط Facebook ساخته شده و همه چیز دارد: runner، assertion، mock، coverage.

terminal
# نصب Jest npm install --save-dev jest # برای TypeScript npm install --save-dev jest @types/jest ts-jest
package.json
{ "scripts": { "test": "jest", "test:watch": "jest --watch", // هر بار فایل تغییر کند، تست‌ها دوباره اجرا می‌شوند "test:coverage": "jest --coverage" // گزارش coverage هم می‌دهد } }

مثال ۱ — اولین تست با Jest

فرض کنید می‌خواهید تابع تقسیم بنویسید. با TDD شروع می‌کنیم:

🔴 مرحله اول — تست بنویسید (هنوز کد نیست)
// math.test.js const { add, divide } = require('./math'); // describe گروه‌بندی می‌کند describe('Math Utils', () => { describe('add()', () => { it('باید دو عدد مثبت را جمع کند', () => { expect(add(2, 3)).toBe(5); }); it('باید با عدد منفی هم کار کند', () => { expect(add(-1, 5)).toBe(4); }); }); describe('divide()', () => { it('باید تقسیم درست انجام دهد', () => { expect(divide(10, 2)).toBe(5); }); it('باید خطا بدهد وقتی تقسیم بر صفر است', () => { // expect می‌کنیم که خطا بدهد expect(() => divide(10, 0)).toThrow('Cannot divide by zero'); }); }); }); // npm test → ❌ FAIL — math.js وجود ندارد
🟢 مرحله دوم — کد بنویسید تا تست pass شود
// math.js function add(a, b) { return a + b; } function divide(a, b) { if (b === 0) { throw new Error('Cannot divide by zero'); } return a / b; } module.exports = { add, divide }; // npm test → ✅ PASS — همه تست‌ها pass شدند

مثال ۲ — Mock کردن

گاهی تابعی که می‌خواهید تست کنید به database یا API خارجی نیاز دارد. در unit test نمی‌خواهیم به database واقعی وصل شویم — کند است و کنترل نداریم. به جایش، database را mock می‌کنیم — یک نسخه fake می‌سازیم که رفتارش قابل کنترل است:

userService.test.js — با Mock
const userService = require('./userService'); const db = require('./database'); // به Jest می‌گوییم database را mock کن — به جای database واقعی استفاده می‌شود jest.mock('./database'); describe('UserService', () => { // قبل از هر تست، همه mock‌ها reset می‌شوند beforeEach(() => { jest.clearAllMocks(); }); it('باید کاربر را با ID برگرداند', async () => { // به mock می‌گوییم وقتی findUser صدا زده شد، این مقدار را برگردان db.findUser.mockResolvedValue({ id: 1, name: 'Ali', email: 'ali@test.com' }); const user = await userService.getUserById(1); // چک می‌کنیم نتیجه درست است expect(user.name).toBe('Ali'); // چک می‌کنیم database با پارامتر درست صدا زده شد expect(db.findUser).toHaveBeenCalledWith(1); expect(db.findUser).toHaveBeenCalledTimes(1); }); it('باید خطا بدهد اگر کاربر پیدا نشود', async () => { db.findUser.mockResolvedValue(null); // کاربر پیدا نشد await expect(userService.getUserById(999)) .rejects .toThrow('User not found'); }); });

Matchers مهم Jest

Matchers توابعی هستند که چک می‌کنند مقدار با انتظار شما برابر است:

matchers.js — راهنمای سریع
// مقایسه مقدار expect(value).toBe(5); // === (برای primitive) expect(obj).toEqual({ a: 1 }); // deep equal (برای object/array) expect(value).not.toBe(5); // not — برعکس هر matcher // null و undefined expect(value).toBeNull(); expect(value).toBeUndefined(); expect(value).toBeDefined(); // true و false expect(value).toBeTruthy(); // هر چیزی که truthy باشد expect(value).toBeFalsy(); // false, 0, '', null, undefined // عدد expect(5).toBeGreaterThan(3); expect(0.1 + 0.2).toBeCloseTo(0.3); // برای floating point // آرایه و string expect([1,2,3]).toContain(2); expect('hello world').toMatch(/world/); expect([1,2]).toHaveLength(2); // خطا expect(() => fn()).toThrow(); expect(() => fn()).toThrow('Error message'); // async await expect(promise).resolves.toBe('value'); await expect(promise).rejects.toThrow();

نکات کلیدی برای مصاحبه

  • TDD چرخه Red → Green → Refactor است. اول تست، بعد کد، بعد بهتر کن.
  • Unit test ایزوله است — هیچ وابستگی خارجی (database، API) نباید داشته باشد.
  • Mock یعنی جایگزین کردن dependency با نسخه fake که رفتارش قابل کنترل است.
  • describe گروه‌بندی می‌کند، it یا test یک تست منفرد تعریف می‌کند.
  • beforeEach/afterEach: قبل/بعد از هر تست اجرا می‌شود — برای setup و cleanup.
  • هدف ۱۰۰٪ coverage نیست — تست‌های معنادار مهم‌تر از تعداد است.
  • در فاز Red باید تست واقعاً fail شود؛ اگر همان اول pass شود، یعنی یا تست اشتباه نوشته شده یا قابلیت از قبل وجود داشته.
  • در فاز Green فقط کمترین کد لازم برای pass شدن نوشته می‌شود — حتی اگر کد زیبا نباشد؛ زیبایی در فاز Refactor می‌آید.
  • سوال رایج: «فرق mock و stub چیست؟» — stub فقط یک مقدار ثابت برمی‌گرداند؛ mock علاوه بر این، رفتار (چند بار صدا زده شد، با چه پارامتری) را هم بررسی می‌کند.
  • یک تله رایج: نوشتن تست بعد از کد و اسمش را TDD گذاشتن — TDD یعنی تست دقیقاً قبل از کد نوشته شود، نه بعدش.
  • Test Pyramid: پایه هرم Unit Testهای زیاد و سریع، وسط Integration Test کمتر، بالای هرم E2E Test خیلی کم — چون E2E کند و شکننده‌تر است.
