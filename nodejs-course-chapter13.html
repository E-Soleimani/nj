Error
Handling

در دنیای واقعی همیشه چیزی می‌تواند اشتباه برود — database وصل نمی‌شود، فایل پیدا نمی‌شود، کاربر داده اشتباه می‌فرستد. یاد می‌گیریم چطور خطاها را به درستی مدیریت کنیم تا برنامه crash نکند و پیام مناسب به کاربر بدهیم.

انواع خطا در Node.js

خطاها در Node.js به چند دسته تقسیم می‌شوند. شناخت هر کدام کمک می‌کند بهتر مدیریتشان کنیم:

SyntaxError

کد نادرست نوشته شده — قبل از اجرا توسط JS engine کشف می‌شود. مثل جا انداختن یک پرانتز.

TypeError

استفاده از چیزی به روش اشتباه — مثل صدا زدن متد روی null یا undefined.

ReferenceError

استفاده از متغیری که وجود ندارد — مثل نوشتن اسم متغیر اشتباه.

Custom Error

خطاهایی که خودتان تعریف می‌کنید — مثل ValidationError، NotFoundError، UnauthorizedError.

try/catch — مدیریت پایه خطا

try/catch اساسی‌ترین روش مدیریت خطا در JavaScript است. کد داخل try اجرا می‌شود. اگر خطایی رخ دهد، به catch می‌رود. finally همیشه اجرا می‌شود — چه خطا بود چه نبود.

try-catch-basic.js
// ساختار اصلی try/catch/finally function divideNumbers(a, b) { try { // این کد ممکن است خطا بدهد if (b === 0) throw new Error('تقسیم بر صفر مجاز نیست'); const result = a / b; console.log(`نتیجه: ${result}`); return result; } catch (error) { // error.message پیام خطا، error.name نوع خطا console.error(`خطا: ${error.message}`); return null; } finally { // این قسمت همیشه اجرا می‌شود — حتی اگر return در try باشد console.log('تابع تمام شد'); } } divideNumbers(10, 2); // نتیجه: 5 // تابع تمام شد divideNumbers(10, 0); // خطا: تقسیم بر صفر مجاز نیست // تابع تمام شد // catch کردن خطاهای مختلف try { const data = JSON.parse('invalid json{'); } catch (error) { if (error instanceof SyntaxError) { console.error('JSON نامعتبر است'); } else { console.error('خطای ناشناخته:', error.message); } }

Custom Error — خطاهای سفارشی

در پروژه‌های واقعی باید خطاهای مختلف را از هم تشخیص دهیم. مثلاً «کاربر پیدا نشد» با «دسترسی رد شد» فرق دارد و HTTP status code متفاوتی دارند. برای این کار Custom Error می‌سازیم:

errors/AppError.js
// کلاس پایه برای همه خطاهای برنامه class AppError extends Error { constructor(message, statusCode = 500, code = 'INTERNAL_ERROR') { super(message); // پیام به Error پایه می‌رود this.name = 'AppError'; this.statusCode = statusCode; // HTTP status code this.code = code; // کد خطا برای client this.isOperational = true; // خطای عملیاتی — نه باگ برنامه Error.captureStackTrace(this, this.constructor); } } // خطاهای مختلف با HTTP status مناسب class NotFoundError extends AppError { constructor(resource = 'Resource') { super(`${resource} not found`, 404, 'NOT_FOUND'); this.name = 'NotFoundError'; } } class ValidationError extends AppError { constructor(message, fields = {}) { super(message, 400, 'VALIDATION_ERROR'); this.name = 'ValidationError'; this.fields = fields; // کدام field اشتباه است } } class UnauthorizedError extends AppError { constructor(message = 'Authentication required') { super(message, 401, 'UNAUTHORIZED'); this.name = 'UnauthorizedError'; } } class ForbiddenError extends AppError { constructor(message = 'Access denied') { super(message, 403, 'FORBIDDEN'); this.name = 'ForbiddenError'; } } module.exports = { AppError, NotFoundError, ValidationError, UnauthorizedError, ForbiddenError };
services/userService.js — استفاده از Custom Error
const { NotFoundError, ValidationError } = require('../errors/AppError'); async function getUserById(id) { // validation if (!id || typeof id !== 'string') { throw new ValidationError('ID must be a valid string', { id: 'Invalid format' }); } const user = await db.findUser(id); if (!user) { throw new NotFoundError('User'); // "User not found" } return user; }

Error Middleware در Express/Fastify

در یک API، به جای اینکه در هر route خطا را مدیریت کنید، یک middleware مرکزی می‌سازید. همه خطاها به این middleware می‌رسند و پاسخ مناسب JSON برمی‌گرداند:

middleware/errorHandler.js
const { AppError } = require('../errors/AppError'); // در Express: middleware با 4 پارامتر = error handler function errorHandler(err, req, res, next) { // اگر خطا از نوع AppError است — خطای عملیاتی if (err instanceof AppError) { return res.status(err.statusCode).json({ success: false, error: { code: err.code, message: err.message, fields: err.fields // فقط در ValidationError } }); } // خطاهای MongoDB if (err.name === 'CastError') { return res.status(400).json({ success: false, error: { code: 'INVALID_ID', message: 'Invalid ID format' } }); } // خطای ناشناخته — باگ برنامه // در production: لاگ بزنید ولی جزئیات به کاربر ندهید console.error('Unexpected error:', err); res.status(500).json({ success: false, error: { code: 'INTERNAL_ERROR', message: process.env.NODE_ENV === 'production' ? 'Something went wrong' // پیام ساده در production : err.message // پیام کامل در development } }); } module.exports = errorHandler;
app.js — استفاده از error handler
const express = require('express'); const errorHandler = require('./middleware/errorHandler'); const { NotFoundError } = require('./errors/AppError'); const app = express(); // routeها اینجا می‌آیند app.use('/api/users', userRoutes); // اگر هیچ route پیدا نشد — 404 app.use((req, res, next) => { next(new NotFoundError('Route')); }); // error handler باید آخر از همه باشد app.use(errorHandler);

Unhandled Errors — خطاهای کنترل‌نشده

بعضی خطاها از try/catch رد می‌شوند — مثل خطاهای async که catch نشده‌اند. Node.js دو event دارد که این‌ها را catch می‌کند:

process-error-handlers.js
// خطاهای async که catch نشده‌اند process.on('unhandledRejection', (reason, promise) => { console.error('🔴 Unhandled Promise Rejection:', reason); // در production: log کنید و gracefully shutdown process.exit(1); }); // خطاهای synchronous کنترل‌نشده process.on('uncaughtException', (error) => { console.error('🔴 Uncaught Exception:', error); // برنامه باید خاتمه یابد — وضعیت نامشخص است process.exit(1); }); // Graceful Shutdown — وقتی SIGTERM می‌آید process.on('SIGTERM', async () => { console.log('SIGTERM received. Shutting down gracefully...'); // اتصال‌های باز را ببندید await db.disconnect(); server.close(() => { console.log('Server closed.'); process.exit(0); }); });

نکات کلیدی برای مصاحبه

  • try/catch فقط خطاهای synchronous را catch می‌کند. برای async از try/catch با await یا .catch() استفاده کنید.
  • Custom Error class بسازید که از Error ارث ببرد — statusCode و code اضافه کنید.
  • خطاهای operational (قابل انتظار مثل 404) را از خطاهای programming (باگ) جدا کنید.
  • در API ها یک error middleware مرکزی بسازید — هر route نباید خودش خطا را format کند.
  • در production جزئیات خطا را به کاربر ندهید — فقط یک پیام ساده. جزئیات را log کنید.
  • unhandledRejection و uncaughtException را handle کنید تا برنامه silently نمیرد.
  • سوال رایج: «فرق خطای operational و programming چیست؟» — operational یعنی خطایی که انتظارش را دارید و بخشی از منطق برنامه است (مثل کاربر پیدا نشد)؛ programming یعنی باگ واقعی در کد (مثل صدا زدن متد روی undefined) که باید اصلاح شود، نه handle.
  • یک تله رایج: catch کردن خطا و هیچ کاری نکردن (catch(e) {}) — خطا را قورت می‌دهد و دیباگ کردن مشکل بعدی را خیلی سخت می‌کند.
  • بعد از uncaughtException، توصیه Node.js این است که برنامه را graceful shutdown کنید و restart شود (مثلاً با PM2) — چون وضعیت داخلی برنامه ممکن است دیگر قابل اعتماد نباشد.
  • در Express/Fastify، اگر یک async route handler خطا throw کند بدون مدیریت، ممکن است برنامه crash کند؛ باید حتماً wrapper یا middleware مخصوص async error داشته باشید.
