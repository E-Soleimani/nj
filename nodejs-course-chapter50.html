Monitoring &
Observability

چطور بفهمیم برنامه در production چه حالی دارد — Structured Logging، Health Checks، Metrics با Prometheus و Distributed Tracing.

PinoHealth ChecksPrometheusTracing

چرا Monitoring حیاتی است؟

وقتی برنامه در production است، نمی‌توانید مثل حالت development console.log را نگاه کنید. Observability یعنی توانایی فهمیدن وضعیت داخلی سیستم فقط از طریق خروجی‌های آن — سه ستون اصلی: Logs، Metrics، Traces.

Structured Logging — لاگ‌های قابل جستجو

console.log('user created') در production بی‌فایده است — قابل جستجو یا فیلتر نیست. Structured logging یعنی لاگ به فرمت JSON با فیلدهای مشخص:

terminal
npm install pino pino-pretty
logger.js
const pino = require('pino'); const logger = pino({ level: process.env.LOG_LEVEL || 'info', // در development، خروجی خوانا؛ در production، JSON خام برای ابزارهای جمع‌آوری transport: process.env.NODE_ENV === 'development' ? { target: 'pino-pretty' } : undefined }); // به جای console.log، از logger با context استفاده کنید logger.info({ userId: '123', action: 'login' }, 'کاربر وارد شد'); // خروجی: {"level":30,"time":..., "userId":"123","action":"login","msg":"کاربر وارد شد"} // حالا می‌توانید در Kibana/Datadog جستجو کنید: userId:"123" logger.error({ err, orderId }, 'پردازش سفارش fail شد'); // child logger — برای اضافه کردن context ثابت (مثل requestId) function requestLogger(req, res, next) { req.log = logger.child({ requestId: generateId(), path: req.path }); req.log.info('درخواست دریافت شد'); next(); }

Health Checks

Kubernetes/Docker/Load Balancer باید بدانند آیا سرویس شما سالم است. دو نوع رایج:

health-checks.js
// Liveness — آیا process اصلاً زنده است؟ // اگر جواب ندهد، orchestrator process را restart می‌کند app.get('/health/live', (req, res) => { res.json({ status: 'ok' }); }); // Readiness — آیا آماده دریافت ترافیک است؟ // چک می‌کند dependencyها (DB, Redis) هم در دسترس‌اند app.get('/health/ready', async (req, res) => { const checks = { database: false, redis: false }; try { await mongoose.connection.db.admin().ping(); checks.database = true; } catch {} try { await redis.ping(); checks.redis = true; } catch {} const isReady = Object.values(checks).every(v => v === true); res.status(isReady ? 200 : 503).json({ status: isReady ? 'ready' : 'not ready', checks }); });

Metrics — اعداد قابل نمودار

Prometheus استاندارد صنعتی برای جمع‌آوری metric است — تعداد request، زمان پاسخ، نرخ خطا:

metrics.js
const client = require('prom-client'); // npm install prom-client // Counter — فقط افزایش پیدا می‌کند (مثل تعداد کل request) const httpRequestsTotal = new client.Counter({ name: 'http_requests_total', help: 'تعداد کل درخواست‌های HTTP', labelNames: ['method', 'route', 'status'] }); // Histogram — توزیع مقادیر (مثل زمان پاسخ) const httpDuration = new client.Histogram({ name: 'http_request_duration_seconds', help: 'مدت زمان پاسخ HTTP', labelNames: ['method', 'route'] }); // middleware — اندازه‌گیری خودکار هر request app.use((req, res, next) => { const end = httpDuration.startTimer(); res.on('finish', () => { httpRequestsTotal.inc({ method: req.method, route: req.path, status: res.statusCode }); end({ method: req.method, route: req.path }); }); next(); }); // endpoint که Prometheus از آن metric را scrape می‌کند app.get('/metrics', async (req, res) => { res.set('Content-Type', client.register.contentType); res.end(await client.register.metrics()); });

Distributed Tracing

وقتی یک request از چند microservice می‌گذرد، Tracing مسیر کامل را نشان می‌دهد — کدام سرویس کند بود، کجا خطا رخ داد. استاندارد امروزی OpenTelemetry است.

💡

سه ستون Observability: Logs (چه اتفاقی افتاد)، Metrics (چقدر/چند بار)، Traces (مسیر یک request خاص در سیستم توزیع‌شده). ابزارهایی مثل Datadog، New Relic، Grafana هر سه را یکجا نشان می‌دهند.

نکات کلیدی برای مصاحبه

  • Structured Logging (JSON) به جای console.log ساده — قابل جستجو در ابزارهای log aggregation.
  • Liveness vs Readiness: liveness یعنی «زنده‌ام»، readiness یعنی «آماده ترافیک هستم» (dependencyها هم سالمند).
  • Prometheus با Counter (فقط افزایش) و Histogram (توزیع مقادیر) metric جمع می‌کند.
  • Distributed Tracing مسیر یک request را بین چند microservice دنبال می‌کند.
  • سه ستون Observability: Logs، Metrics، Traces — هر کدام سوال متفاوتی جواب می‌دهند.
  • هرگز داده حساس (پسورد، توکن) را در لاگ چاپ نکنید — حتی به صورت اشتباهی.
  • سوال رایج: «چرا فقط Log کافی نیست و به Metrics هم نیاز داریم؟» — Log برای بررسی یک اتفاق خاص خوب است (مثلاً چرا این request fail شد)؛ Metrics برای دید کلی و روند در طول زمان است (مثلاً میانگین زمان پاسخ در ساعت گذشته) — جستجو در میلیون‌ها لاگ برای این کار عملی نیست.
  • یک تله رایج: چک کردن فقط Liveness و فراموش کردن Readiness — سرور ممکن است «زنده» باشد ولی چون به دیتابیس وصل نیست، همه request‌ها fail شوند؛ Load Balancer باید فقط instanceهای Ready را ترافیک بدهد.
  • Trace ID یک شناسه یکتا برای هر request است که در تمام سرویس‌هایی که آن request از آن‌ها عبور می‌کند حمل می‌شود — این باعث می‌شود بتوانید مسیر کامل یک درخواست را در سیستم‌های توزیع‌شده دنبال کنید.
  • ابزارهایی مثل Datadog، Grafana، New Relic هر سه ستون Observability را در یک dashboard واحد نشان می‌دهند تا نیازی به بررسی جدا جدا نباشد.
