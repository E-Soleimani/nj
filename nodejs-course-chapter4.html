Semantic
Versioning

وقتی یک پکیج npm نصب می‌کنید، اعداد کنار نامش مثل 4.18.2 یا ^1.4.0 چه معنایی دارند؟ در این فصل یاد می‌گیریم Semantic Versioning چیست و چطور در npm استفاده می‌شود.

MAJOR MINOR PATCH ^ caret ~ tilde

SemVer چیست؟

Semantic Versioning (SemVer) یک قرارداد جهانی است که می‌گوید نسخه‌های نرم‌افزار باید به صورت MAJOR.MINOR.PATCH باشند — مثل 2.4.1. هر عدد معنای دقیقی دارد و به کاربران می‌گوید آپدیت جدید چقدر تغییر ایجاد کرده.

چرا مهم است؟ وقتی npm می‌نویسد "express": "^4.18.2"، باید بدانید آیا آپدیت بعدی express ممکن است کد شما را بشکند یا نه. SemVer این را مشخص می‌کند.

معنای هر عدد

🔴 MAJOR — تغییر بزرگ (Breaking Change)

وقتی عدد اول تغییر کند، یعنی تغییرات بزرگی اتفاق افتاده که ممکن است کد شما دیگر کار نکند. مثلاً تابعی که قبلاً وجود داشت حذف شده، یا پارامترهایش عوض شده. قبل از آپدیت MAJOR، باید documentation را بخوانید و تست کنید.

🟡 MINOR — قابلیت جدید (Backward-Compatible)

وقتی عدد دوم تغییر کند، یعنی قابلیت جدیدی اضافه شده ولی هیچ چیزی نشکسته. کد قدیمی شما بدون تغییر کار می‌کند. می‌توانید با خیال راحت آپدیت کنید.

🟢 PATCH — رفع باگ (Backward-Compatible)

وقتی عدد سوم تغییر کند، یعنی فقط باگی رفع شده. هیچ چیز جدیدی اضافه نشده، هیچ چیزی نشکسته. معمولاً همیشه آپدیت PATCH را نصب کنید.

semver-examples.txt
# PATCH — فقط باگ fix شده 1.0.0 → 1.0.1 یک باگ رفع شد، همه چیز سر جایش است # MINOR — قابلیت جدید اضافه شده 1.0.0 → 1.1.0 یک feature جدید اضافه شد، کد قدیمی کار می‌کند # MAJOR — تغییر بنیادی 1.0.0 → 2.0.0 API عوض شد، کد قدیمی ممکن است نشکند! # مثال واقعی — Express 4.17.0 → 4.17.1 باگ fix — safe 4.17.1 → 4.18.0 feature جدید — safe 4.x.x → 5.0.0 breaking change — باید تست کنید!

Version Ranges در package.json

وقتی در package.json نسخه پکیج را مشخص می‌کنید، علامت‌هایی مثل ^ و ~ تعیین می‌کنند که چه آپدیت‌هایی مجاز هستند:

^

Caret — پیش‌فرض npm

MINOR و PATCH آپدیت مجاز است. MAJOR نه.
^4.18.2 یعنی 4.x.x

~

Tilde — محافظه‌کارانه

فقط PATCH آپدیت مجاز است.
~4.18.2 یعنی 4.18.x

=

Exact — دقیقاً همین

فقط همین نسخه نصب می‌شود. هیچ آپدیتی مجاز نیست.

*

Wildcard — هر نسخه‌ای

خطرناک! هر نسخه‌ای نصب می‌شود. در production استفاده نکنید.

package.json — مثال‌های واقعی
{ "dependencies": { "express": "^4.18.2", // 4.18.2 یا بالاتر، ولی نه 5.0.0 "lodash": "~4.17.21", // 4.17.21 یا بالاتر، ولی نه 4.18.0 "dotenv": "16.3.1", // دقیقاً همین نسخه "axios": ">=1.0.0", // 1.0.0 یا بالاتر "moment": "*" // هر نسخه — خطرناک! } }
💡

وقتی npm install می‌کنید: npm به صورت خودکار ^ می‌گذارد. یعنی npm install express در package.json می‌نویسد "express": "^4.18.2". پس آپدیت‌های MINOR خودکار نصب می‌شوند.

Pre-release Versions

قبل از انتشار یک نسخه رسمی، معمولاً مراحلی مثل alpha و beta وجود دارد. این‌ها نسخه‌های آزمایشی هستند:

pre-release-stages.txt
1.0.0-alpha ← خیلی ناپایدار، فقط برای تست اولیه 1.0.0-alpha.2 ← دومین نسخه alpha 1.0.0-beta ← پایدارتر از alpha، ولی هنوز ممکن است باگ داشته باشد 1.0.0-beta.3 ← سومین نسخه beta 1.0.0-rc.1 ← Release Candidate — تقریباً آماده انتشار 1.0.0 ← نسخه رسمی و پایدار # ترتیب اولویت: # alpha < beta < rc < release

نکات کلیدی برای مصاحبه

  • MAJOR: تغییر breaking — ممکن است کد قدیمی کار نکند. قبل از آپدیت تست کنید.
  • MINOR: feature جدید سازگار با قبل — کد قدیمی کار می‌کند. آپدیت امن است.
  • PATCH: bugfix — هیچ چیز نشکسته. همیشه آپدیت کنید.
  • علامت ^ (caret) پیش‌فرض npm است — MINOR آپدیت‌ها را قبول می‌کند.
  • علامت ~ (tilde) محافظه‌کارانه‌تر است — فقط PATCH آپدیت‌ها.
  • نسخه 0.x.x یعنی هنوز پایدار نشده — هر تغییری ممکن است کد را بشکند.
  • فایل package-lock.json نسخه دقیق نصب‌شده را ذخیره می‌کند — برای reproducible builds.
  • ترتیب همیشه یکسان است: MAJOR.MINOR.PATCH، مثل ۲.۴.۱ — عدد اول از همه مهم‌تر است.
  • اگر عدد اول ثابت باشد ولی نسخه جدید بیاید (مثل 4.19.0 به جای 4.18.2)، طبق قرارداد semver نباید هیچ کد قدیمی‌ای بشکند.
  • سوال رایج: «اگر یک کتابخانه نسخه 0.5.0 دارد یعنی چه؟» — یعنی هنوز به نسخه پایدار 1.0.0 نرسیده؛ API آن ممکن است هر لحظه تغییر کند، پس با احتیاط استفاده شود.
  • یک تله رایج: خیلی‌ها فکر می‌کنند فقط با رعایت semver توسط سازنده پکیج مشکلی پیش نمی‌آید — ولی همه پکیج‌ها این قرارداد را دقیق رعایت نمی‌کنند، پس تست کردن بعد از هر آپدیت (حتی MINOR) عاقلانه است.
