Pub/Sub
توزیع‌شده با Redis

وقتی برنامه شما با چند instance (cluster) اجرا می‌شود، EventEmitter کافی نیست. یاد می‌گیریم با Redis Pub/Sub رویدادها را بین process‌های مختلف sync کنیم.

Redis Pub/SubClusterSocket.io AdapterDistributed Events

محدودیت EventEmitter — فقط در یک Process

EventEmitter که در فصل قبل دیدیم، فقط داخل یک process کار می‌کند. اگر برنامه شما با Cluster یا چند سرور اجرا شود، هر process یک EventEmitter جدا دارد — رویدادی که در process یک emit می‌شود، در process دو دیده نمی‌شود. این مشکل را Pub/Sub توزیع‌شده با Redis حل می‌کند.

چرا مهم است؟ فرض کنید با PM2 یا cluster، 4 instance از سرور chat را اجرا کرده‌اید. کاربر A به instance 1 وصل است، کاربر B به instance 3. وقتی A پیام می‌فرستد، باید به B هم برسد — ولی آن‌ها در process های جدا هستند!

Redis Pub/Sub — راه‌حل توزیع‌شده

Redis یک مکانیزم Publish/Subscribe دارد: یک process چیزی را در یک کانال (channel) منتشر می‌کند، همه process‌هایی که به آن کانال subscribe کرده‌اند، آن را دریافت می‌کنند — حتی اگر روی سرورهای مختلف باشند.

pubsub-basic.js
const Redis = require('ioredis'); // نکته مهم: برای pub/sub باید دو connection جدا داشته باشید // یکی فقط برای publish، یکی فقط برای subscribe const publisher = new Redis(); const subscriber = new Redis(); // subscribe — این process به کانال 'notifications' گوش می‌دهد subscriber.subscribe('notifications', (err, count) => { console.log(`Subscribed به ${count} کانال`); }); // وقتی پیامی روی این کانال منتشر شود، این callback اجرا می‌شود subscriber.on('message', (channel, message) => { console.log(`[${channel}] دریافت شد: ${message}`); const data = JSON.parse(message); // مثلاً پیام را به socket مربوطه بفرستیم }); // publish — این process یک پیام منتشر می‌کند // همه subscriberها (حتی روی سرورهای دیگر) آن را می‌گیرند publisher.publish('notifications', JSON.stringify({ userId: '123', message: 'سفارش شما تایید شد' }));

کاربرد واقعی — Chat با چند Instance

یادتان هست در فصل ۱۸ یک chat server با Socket.io ساختیم؟ اگر آن سرور را با Cluster اجرا کنیم، باید Redis Adapter اضافه کنیم تا پیام‌ها بین instanceها sync شوند:

socket-redis-adapter.js
const { Server } = require('socket.io'); const { createAdapter } = require('@socket.io/redis-adapter'); const Redis = require('ioredis'); const io = new Server(httpServer); const pubClient = new Redis(); const subClient = pubClient.duplicate(); // با این یک خط، Socket.io خودکار از Redis Pub/Sub استفاده می‌کند // هر io.emit() در یک instance، به همه instanceها sync می‌شود io.adapter(createAdapter(pubClient, subClient)); // از اینجا به بعد، کد شما هیچ تغییری نمی‌خواهد! // io.to(room).emit() همان قبلی است — ولی الان بین همه instanceها کار می‌کند io.on('connection', (socket) => { socket.on('message', (data) => { io.to(data.room).emit('message', data); // اگر کاربر دیگری در instance دیگری در همان room باشد، // پیام به او هم می‌رسد — به لطف Redis Adapter }); });

Pub/Sub vs Message Queue — تفاوت مهم

Pub/Sub (Redis)

پیام به همه subscriberهای فعال می‌رسد

اگر subscriber آنلاین نباشد، پیام را از دست می‌دهد

مناسب: notification، real-time sync بین serverها

Message Queue (در فصل بعد)

پیام در صف می‌ماند تا consumer آن را بردارد

اگر consumer آفلاین باشد، پیام گم نمی‌شود

مناسب: task processing، job که حتماً باید انجام شود

⚠️

نکته حیاتی: Redis Pub/Sub at-most-once delivery دارد — اگر subscriber در لحظه publish آنلاین نباشد، پیام برای همیشه گم می‌شود. برای کارهای حساس (مثل پردازش پرداخت) از Message Queue استفاده کنید، نه Pub/Sub.

نکات کلیدی برای مصاحبه

  • EventEmitter فقط درون یک process کار می‌کند. Pub/Sub توزیع‌شده بین چند process/سرور.
  • در Redis Pub/Sub باید دو connection جدا داشته باشید — یکی publish، یکی subscribe.
  • Redis Pub/Sub پیام را ذخیره نمی‌کند — اگر subscriber آفلاین باشد، پیام گم می‌شود.
  • @socket.io/redis-adapter به Socket.io اجازه می‌دهد روی چند instance scale شود.
  • برای کارهای حساس که نباید گم شوند، Pub/Sub کافی نیست — به Message Queue نیاز دارید (فصل بعد).
  • سوال رایج: «چرا با چند instance سرور، EventEmitter کافی نیست؟» — چون هر process حافظه جدا دارد؛ EventEmitter در process ۱ فقط توسط listenerهای همان process شنیده می‌شود، نه process ۲.
  • یک تله رایج: فرض کردن Redis Pub/Sub مثل صف است و پیام را نگه می‌دارد — اشتباه است؛ اگر در لحظه انتشار پیام هیچ subscriber فعالی نباشد، پیام برای همیشه از دست می‌رود.
  • Pub/Sub مدل at-most-once delivery دارد (حداکثر یک بار، ممکن است صفر بار)؛ Message Queue معمولاً at-least-once (حداقل یک بار، تضمین تحویل).
  • کاربرد رایج Pub/Sub: sync کردن حالت بین چند instance سرور، مثل اطلاع‌رسانی real-time یا هماهنگی cache invalidation.
