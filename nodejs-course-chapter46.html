Authorization
& RBAC

بعد از احراز هویت، باید مشخص کنیم کاربر اجازه چه کاری دارد — از RBAC ساده تا ABAC پیچیده‌تر با چک ویژگی‌های چندگانه.

RBACPermissionsOwnership CheckABAC

Authorization چیست؟

بعد از اینکه فهمیدیم کاربر کیست (Authentication)، باید بفهمیم اجازه چه کاری را دارد. مثلاً هر دو کاربر «Ali» و «Admin» احراز هویت شده‌اند، ولی فقط Admin اجازه حذف کاربران دیگر را دارد.

RBAC — Role-Based Access Control

ساده‌ترین و رایج‌ترین مدل: هر کاربر یک یا چند نقش (role) دارد، و هر نقش مجموعه‌ای از مجوزها (permissions).

rbac-basic.js
// تعریف نقش‌ها و مجوزهایشان const ROLES = { user: { permissions: ['read:own_profile', 'update:own_profile'] }, editor: { permissions: ['read:own_profile', 'update:own_profile', 'create:post', 'update:post'] }, admin: { permissions: ['read:any_profile', 'update:any_profile', 'delete:user', 'create:post', 'delete:post'] }, }; function hasPermission(userRole, requiredPermission) { const role = ROLES[userRole]; if (!role) return false; return role.permissions.includes(requiredPermission); } console.log(hasPermission('user', 'delete:user')); // false console.log(hasPermission('admin', 'delete:user')); // true

پیاده‌سازی به عنوان Middleware

middleware/authorize.js
// یک middleware factory — پارامتر می‌گیرد و middleware می‌سازد (curry از فصل 24!) function authorize(requiredPermission) { return function(req, res, next) { // req.user از middleware authenticate می‌آید (فصل قبل) if (!req.user) { return res.status(401).json({ error: 'ابتدا لاگین کنید' }); } if (!hasPermission(req.user.role, requiredPermission)) { return res.status(403).json({ error: 'دسترسی غیرمجاز' }); } next(); }; } // استفاده — خیلی خوانا app.delete('/users/:id', authenticate, authorize('delete:user'), async (req, res) => { await userService.delete(req.params.id); res.status(204).send(); }); app.post('/posts', authenticate, authorize('create:post'), async (req, res) => { // فقط editor و admin به اینجا می‌رسند });

Resource-Based Authorization — چک کردن مالکیت

RBAC خالص کافی نیست وقتی کاربر باید فقط منابع خودش را ویرایش کند (نه هر user دیگری با همان role). این نیاز به چک کردن اضافی روی resource دارد:

ownership-check.js
// middleware که مالکیت را چک می‌کند function requireOwnership(resourceType) { return async function(req, res, next) { const resource = await db[resourceType].findById(req.params.id); if (!resource) { return res.status(404).json({ error: 'یافت نشد' }); } // admin همیشه اجازه دارد — یا owner باشد const isOwner = resource.userId === req.user.userId; const isAdmin = req.user.role === 'admin'; if (!isOwner && !isAdmin) { return res.status(403).json({ error: 'فقط مالک یا ادمین اجازه دارد' }); } req.resource = resource; // برای استفاده در handler بعدی، دوباره query نزنیم next(); }; } // استفاده — کاربر فقط پست خودش را می‌تواند ویرایش کند app.put('/posts/:id', authenticate, requireOwnership('posts'), async (req, res) => { const updated = await postService.update(req.resource.id, req.body); res.json(updated); });

ABAC — Attribute-Based Access Control

وقتی RBAC خیلی ساده است، ABAC تصمیم‌گیری را بر اساس ویژگی‌های کاربر، منبع و context انجام می‌دهد — مثلاً «فقط در ساعات کاری» یا «فقط از IP داخلی»:

abac-example.js
// یک policy تابعی است که true/false برمی‌گرداند const policies = { canEditDocument: (user, document, context) => { if (user.role === 'admin') return true; if (document.ownerId !== user.id) return false; if (document.status === 'locked') return false; // چک زمانی — فقط ساعات کاری const hour = new Date().getHours(); if (hour < 9 || hour > 18) return false; return true; } }; function can(policyName) { return async function(req, res, next) { const resource = await db.findById(req.params.id); if (!policies[policyName](req.user, resource, req)) { return res.status(403).json({ error: 'دسترسی رد شد' }); } next(); }; }

نکات کلیدی برای مصاحبه

  • RBAC: کاربر نقش دارد، نقش مجوز دارد — ساده و رایج‌ترین مدل.
  • Resource-based / Ownership check: علاوه بر role، باید مالکیت منبع را هم چک کنید.
  • ABAC: تصمیم‌گیری بر اساس ویژگی‌های چندگانه (زمان، مکان، وضعیت منبع) — انعطاف بیشتر از RBAC.
  • خطای Authorization باید 403 Forbidden باشد — نه 401 (که برای Authentication است).
  • middleware factory (تابعی که middleware می‌سازد) الگوی رایج برای authorize با پارامتر است.
  • همیشه چک‌های authorization را در سرور انجام دهید — هرگز فقط به UI اعتماد نکنید.
  • سوال رایج: «چرا RBAC به‌تنهایی گاهی کافی نیست؟» — RBAC فقط بر اساس نقش تصمیم می‌گیرد، نه مالکیت؛ مثلاً دو کاربر با نقش «user» نباید بتوانند پست‌های همدیگر را ویرایش کنند، پس باید Ownership check هم اضافه شود.
  • یک تله رایج: چک کردن دسترسی فقط در frontend (مثلاً مخفی کردن دکمه حذف) — کاربر می‌تواند مستقیم به API درخواست بزند و از این چک عبور کند؛ چک واقعی همیشه باید سمت سرور باشد.
  • Permission-based نسبت به Role-based انعطاف بیشتری دارد — به جای «این role این کارها را می‌کند»، مستقیم «این کاربر این مجوزها را دارد»، که امکان تنظیم دقیق‌تر می‌دهد.
  • در سیستم‌های بزرگ، معمولاً ترکیبی از RBAC (برای دسته‌بندی کلی) و Resource-based check (برای جزئیات دقیق) با هم استفاده می‌شود.
