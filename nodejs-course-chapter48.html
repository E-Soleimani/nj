فراتر از Redis Cache ساده

در فصل ۲۱ الگوی Cache-Aside را با Redis دیدیم. در این فصل عمیق‌تر می‌رویم: استراتژی‌های مختلف caching، HTTP caching headers، و invalidation — یکی از سخت‌ترین مسائل در برنامه‌نویسی.

جمله معروف در دنیای برنامه‌نویسی: «فقط دو چیز سخت در علوم کامپیوتر وجود دارد: cache invalidation و نامگذاری چیزها.» — Phil Karlton

سه استراتژی اصلی Caching

Cache-Aside (Lazy Loading)

اپلیکیشن اول cache چک می‌کند، اگر نبود از DB می‌گیرد و cache می‌کند. (فصل 21)

Write-Through

هر نوشتن هم‌زمان در DB و Cache انجام می‌شود — cache همیشه به‌روز است.

Write-Behind (Write-Back)

نوشتن ابتدا در Cache، بعد به صورت async در DB — سریع‌تر ولی خطر از دست دادن داده.

Write-Through — پیاده‌سازی

write-through.js
async function updateUser(id, data) { // هر دو با هم به‌روز می‌شوند — cache همیشه sync است const user = await User.findByIdAndUpdate(id, data, { new: true }); await redis.setex(`user:${id}`, 3600, JSON.stringify(user)); return user; } // مزیت: کاربر بعدی همیشه داده تازه از cache می‌گیرد — نیاز به invalidate جدا نیست

HTTP Caching — کش در لایه شبکه

قبل از اینکه request حتی به سرور برسد، مرورگر یا CDN می‌تواند پاسخ را از cache خودش بدهد. این با headerهای HTTP کنترل می‌شود:

http-caching-headers.js
app.get('/products/:id', async (req, res) => { const product = await productService.findById(req.params.id); // Cache-Control — به مرورگر/CDN می‌گوید چقدر cache کند res.set('Cache-Control', 'public, max-age=3600'); // 1 ساعت // ETag — یک "امضا" برای محتوا. اگر تغییر نکرده، فقط 304 برمی‌گردد // بدون فرستادن دوباره کل داده const etag = generateETag(product); res.set('ETag', etag); // چک کردن اگر مرورگر همان نسخه را دارد if (req.headers['if-none-match'] === etag) { return res.status(304).end(); // Not Modified — بدون body } res.json(product); }); // انواع Cache-Control: // public → همه (شامل CDN) می‌توانند cache کنند // private → فقط مرورگر کاربر cache کند، نه CDN مشترک // no-cache → قبل از استفاده باید revalidate شود // no-store → هیچ‌جا cache نشود — برای داده حساس

Cache Invalidation — دقیق‌ترین بخش

استراتژی TTL — ساده‌ترین

ttl-strategy.js
// فقط منتظر بمانید تا cache خودش منقضی شود — ساده ولی داده قدیمی موقتاً نمایش داده می‌شود await redis.setex('products:list', 300, data); // 5 دقیقه

استراتژی Event-Based — دقیق‌تر

event-based-invalidation.js
// وقتی داده تغییر می‌کند، فوراً cache مرتبط را پاک کنید async function updateProduct(id, data) { const product = await Product.findByIdAndUpdate(id, data, { new: true }); // پاک کردن همه cacheهای مرتبط await redis.del(`product:${id}`); await redis.del('products:list'); // لیست هم شامل این محصول بود // یا با Pub/Sub (فصل 32) به همه instanceها اطلاع بدهید await redisPublisher.publish('cache:invalidate', JSON.stringify({ key: `product:${id}` })); return product; } // Cache Tagging — گروه‌بندی برای invalidation دسته‌جمعی async function invalidateByTag(tag) { const keys = await redis.smembers(`tag:${tag}`); // همه keyهای این tag if (keys.length > 0) { await redis.del(...keys); } }

CDN — Cache در لبه شبکه

برای فایل‌های static (تصاویر، CSS، JS) و حتی API response‌های عمومی، CDN (Content Delivery Network) مثل Cloudflare محتوا را نزدیک به کاربر cache می‌کند — درخواست اصلاً به سرور شما نمی‌رسد:

💡

تفاوت لایه‌های caching: Browser Cache (نزد کاربر) → CDN (نزدیک کاربر جغرافیایی) → Redis/Application Cache (نزد سرور) → Database. هرچقدر جلوتر cache شود، سریع‌تر و بار سرور کمتر است.

نکات کلیدی برای مصاحبه

  • Cache-Aside: خواندن lazy. Write-Through: نوشتن sync با cache. Write-Behind: نوشتن async — سریع‌تر ولی ریسک.
  • ETag + 304 Not Modified: جلوگیری از انتقال داده تکراری وقتی چیزی تغییر نکرده.
  • Cache-Control headerها به مرورگر/CDN می‌گویند چه مدت و چطور cache کنند.
  • Cache Invalidation سخت‌ترین بخش است — یا با TTL (ساده) یا Event-based (دقیق‌تر).
  • Cache Tagging برای invalidate دسته‌جمعی چند key مرتبط با یک رویداد.
  • لایه‌های caching از نزدیک‌ترین به کاربر تا دورترین: Browser → CDN → Redis → Database.
  • سوال رایج: «چرا Cache Invalidation سخت است؟» — چون باید دقیقاً بدانید چه زمانی داده تغییر کرده و کدام cacheهای مرتبط باید پاک شوند؛ اگر دیر پاک شود کاربر داده قدیمی می‌بیند، اگر زیادی زود/مکرر پاک شود مزیت cache از بین می‌رود.
  • یک تله رایج: گذاشتن TTL خیلی طولانی «برای کاهش بار دیتابیس» بدون Event-based invalidation — کاربر ممکن است دقیقه‌ها یا ساعت‌ها داده قدیمی ببیند بعد از یک تغییر مهم.
  • Stale-While-Revalidate یک استراتژی پیشرفته است: داده قدیمی cache فوراً نمایش داده می‌شود درحالی‌که در پس‌زمینه نسخه تازه گرفته می‌شود — تجربه کاربری سریع با داده نسبتاً تازه.
  • Write-Behind سریع‌ترین است چون نوشتن فقط در cache انجام می‌شود و بعداً async به دیتابیس می‌رود، ولی اگر سرور قبل از sync کردن crash کند، داده از دست می‌رود.
