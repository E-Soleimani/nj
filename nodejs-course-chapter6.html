Git
Flow

Git Flow یک استراتژی branching است که به تیم‌ها می‌گوید چه branchهایی داشته باشند، کد چطور بین آن‌ها جابجا شود، و چطور release مدیریت شود. در اکثر شرکت‌ها از این مدل یا مشابه آن استفاده می‌شود.

main develop feature release hotfix

مشکلی که Git Flow حل می‌کند

تصور کنید سه نفر روی یک پروژه کار می‌کنند. یکی روی feature جدید، دیگری باگ fix می‌کند، و سومی دارد نسخه جدید release می‌دهد. اگر همه روی یک branch (main) کار کنند، chaos است. Git Flow می‌گوید: «برای هر کار یک branch مشخص وجود دارد.»

Git Flow توسط Vincent Driessen در ۲۰۱۰ معرفی شد. یک قرارداد تیمی است — نه یک ابزار. همه با هم تصمیم می‌گیرند از این قوانین پیروی کنند تا کد منظم بماند.

پنج نوع Branch در Git Flow

main

کد production — آنچه روی سرور اجرا می‌شود. همیشه پایدار و قابل deploy است. هیچ‌وقت مستقیم به آن push نمی‌کنیم.

develop

آخرین تغییرات توسعه. همه featureهای کامل‌شده اینجا merge می‌شوند. پایه همه feature branchهای جدید است.

feature/*

برای هر قابلیت جدید. از develop می‌آید و به develop برمی‌گردد. مثال: feature/user-login

release/*

آماده‌سازی نسخه جدید برای release. فقط bugfix — نه feature جدید. به main و develop merge می‌شود.

hotfix/*

تنها branch‌ای که از main می‌آید — برای باگ‌های اورژانسی production. باید سریع fix شود و به main و develop هر دو merge شود. مثال: hotfix/payment-crash

چرخه کامل یک Feature

یک developer می‌خواهد feature «احراز هویت کاربر» را بنویسد. مراحل دقیق در Git Flow:

terminal — feature workflow کامل
— مرحله ۱: از develop شروع کنید — git checkout develop git pull origin develop # آخرین تغییرات را بگیرید — مرحله ۲: branch feature بسازید — git checkout -b feature/user-authentication — مرحله ۳: کد بنویسید و commit کنید — git add . git commit -m "feat: add JWT token generation" git commit -m "feat: add login/logout endpoints" git commit -m "feat: add password hashing with bcrypt" git commit -m "test: add authentication unit tests" — مرحله ۴: وقتی تمام شد، به develop merge کنید — git checkout develop git merge --no-ff feature/user-authentication # --no-ff یعنی حتماً یک merge commit بساز # این کار در تاریخچه واضح نشان می‌دهد این تغییرات از یک feature branch آمدند git push origin develop — مرحله ۵: branch را حذف کنید — git branch -d feature/user-authentication
💡

چرا --no-ff؟ بدون این flag، اگر تاریخچه خطی باشد، Git یک fast-forward انجام می‌دهد و merge commit نمی‌سازد. با --no-ff همیشه merge commit داریم که نشان می‌دهد این تغییرات از یک feature branch آمدند.

چرخه Release

وقتی develop آماده انتشار شد، یک branch release می‌سازیم. در این branch فقط bugfix مجاز است — نه feature جدید. بعد به main و develop هر دو merge می‌شود:

terminal — release workflow
— شروع release از develop — git checkout develop git checkout -b release/2.1.0 — فقط bugfix در این branch — git commit -m "fix: correct version number in config" git commit -m "fix: fix typo in error message" — merge به main (deploy می‌شود) — git checkout main git merge --no-ff release/2.1.0 git tag -a v2.1.0 -m "Release version 2.1.0" # tag می‌زنیم — merge به develop هم (تا bugfixها از دست نرود) — git checkout develop git merge --no-ff release/2.1.0 — push همه چیز — git push origin main develop git push origin --tags # tagها را هم push کنید git branch -d release/2.1.0

Hotfix — باگ اورژانسی

فرض کنید سیستم پرداخت در production crash می‌کند. باید فوری fix شود — نمی‌توان منتظر develop ماند. hotfix مستقیم از main می‌آید:

terminal — hotfix اورژانسی
— از main شروع کنید (نه develop!) — git checkout main git checkout -b hotfix/payment-null-pointer — باگ را fix کنید — git commit -m "fix: resolve null pointer in payment processing" git commit -m "test: add regression test for payment fix" — به main merge کنید و tag بزنید — git checkout main git merge --no-ff hotfix/payment-null-pointer git tag -a v2.1.1 -m "Hotfix: payment crash" — به develop هم merge کنید تا fix از دست نرود — git checkout develop git merge --no-ff hotfix/payment-null-pointer git push origin main develop --tags git branch -d hotfix/payment-null-pointer
⚠️

فراموش نکنید: hotfix را به هر دوی main و develop merge کنید. اگر فقط به main merge کنید، در release بعدی آن fix از develop نمی‌آید و باگ دوباره ظاهر می‌شود!

GitHub Flow — گزینه ساده‌تر

Git Flow برای پروژه‌های بزرگ با release cycle منظم خوب است. برای تیم‌های کوچک یا پروژه‌هایی که هر روز deploy می‌کنند، GitHub Flow ساده‌تر است: فقط main + feature branches. هر feature بعد از review مستقیم به main می‌رود و deploy می‌شود.

نکات کلیدی برای مصاحبه

  • main: همیشه پایدار، قابل deploy. هیچ‌وقت مستقیم push نکنید.
  • develop: پایه همه featureها. integration branch است.
  • feature/*: از develop، به develop. یک feature = یک branch.
  • release/*: فقط bugfix. نه feature جدید. به main و develop merge می‌شود.
  • hotfix/*: تنها branch‌ای که از main می‌آید — باگ‌های اورژانسی.
  • hotfix و release را به هر دوی main و develop merge کنید — نه یکی.
  • از --no-ff استفاده کنید تا merge commitها در تاریخچه واضح باشند.
  • ترتیب شاخه‌ها از پایدارترین به ناپایدارترین: main (production) → release (آماده‌سازی نسخه) → develop (یکپارچه‌سازی) → feature (کار روزانه).
  • سوال رایج: «چرا hotfix از main می‌آید نه از develop؟» — چون باگ فوری در production است؛ develop ممکن است feature‌های ناتمام داشته باشد که هنوز آماده انتشار نیستند.
  • یک تله رایج: فراموش کردن merge کردن hotfix به develop — نتیجه‌اش این می‌شود که همان باگ دوباره در نسخه بعدی develop ظاهر می‌شود.
  • Git Flow برای پروژه‌های با چرخه انتشار مشخص (نسخه ۱٫۰، ۱٫۱، ...) مناسب است؛ برای تیم‌هایی که هر روز چند بار deploy می‌کنند (مثل خیلی از استارتاپ‌ها)، مدل‌های ساده‌تر مثل Trunk-Based Development رایج‌تر است.
