TypeORM
ORM برای TypeScript

به جای نوشتن SQL خام، با TypeORM کار با PostgreSQL را به سبک شیء‌گرا و type-safe انجام می‌دهیم — با Entity، Repository و Migration.

EntityRepositoryMigrationsQueryBuilder

TypeORM چیست؟

نوشتن SQL خام برای هر query خسته‌کننده و خطاپذیر است. TypeORM یک ORM (Object-Relational Mapping) است — جدول‌های دیتابیس را به کلاس‌های TypeScript تبدیل می‌کند. با آن، به جای SQL، با object و متد کار می‌کنید — شبیه Mongoose ولی برای SQL.

نصب و راه‌اندازی

terminal
npm install typeorm reflect-metadata pg # reflect-metadata برای decoratorها لازم است

تعریف Entity — معادل Table

entities/User.ts
import { Entity, PrimaryGeneratedColumn, Column, OneToMany, CreateDateColumn } from 'typeorm'; import { Order } from './Order'; // @Entity — این class معادل یک جدول است @Entity('users') export class User { @PrimaryGeneratedColumn() // معادل SERIAL PRIMARY KEY id: number; @Column({ length: 100 }) name: string; @Column({ unique: true }) email: string; @Column({ nullable: true }) age: number; @CreateDateColumn() // خودکار زمان ساخت را ثبت می‌کند createdAt: Date; // رابطه یک به چند — یک User چند Order دارد @OneToMany(() => Order, order => order.user) orders: Order[]; }
entities/Order.ts
import { Entity, PrimaryGeneratedColumn, Column, ManyToOne } from 'typeorm'; import { User } from './User'; @Entity('orders') export class Order { @PrimaryGeneratedColumn() id: number; @Column('decimal') total: number; // رابطه چند به یک — چند Order به یک User تعلق دارند @ManyToOne(() => User, user => user.orders) user: User; }

اتصال به Database

data-source.ts
import { DataSource } from 'typeorm'; import { User } from './entities/User'; import { Order } from './entities/Order'; export const AppDataSource = new DataSource({ type: 'postgres', host: process.env.DB_HOST, port: 5432, username: process.env.DB_USER, password: process.env.DB_PASSWORD, database: process.env.DB_NAME, entities: [User, Order], synchronize: false, // در production همیشه false — از migration استفاده کنید logging: process.env.NODE_ENV === 'development' }); // در server.ts await AppDataSource.initialize(); console.log('اتصال به دیتابیس برقرار شد');

CRUD با Repository Pattern

services/userService.ts
import { AppDataSource } from '../data-source'; import { User } from '../entities/User'; // getRepository — ابزار کار با یک Entity خاص const userRepository = AppDataSource.getRepository(User); // CREATE async function createUser(data: Partial<User>) { const user = userRepository.create(data); // فقط instance می‌سازد — هنوز save نشده return userRepository.save(user); // حالا در دیتابیس ذخیره می‌شود } // READ async function getUserById(id: number) { return userRepository.findOne({ where: { id }, relations: ['orders'] // معادل populate در Mongoose — JOIN خودکار }); } async function getAllUsers() { return userRepository.find({ where: { age: MoreThan(18) }, // import { MoreThan } from 'typeorm' order: { createdAt: 'DESC' }, take: 10 // معادل LIMIT }); } // UPDATE async function updateUser(id: number, data: Partial<User>) { await userRepository.update(id, data); return getUserById(id); } // DELETE async function deleteUser(id: number) { return userRepository.delete(id); } // Query Builder — برای query‌های پیچیده‌تر async function getUsersWithOrderStats() { return userRepository .createQueryBuilder('user') .leftJoinAndSelect('user.orders', 'order') .where('user.age > :age', { age: 18 }) .orderBy('user.createdAt', 'DESC') .getMany(); }

Migrations — تغییرات ساختار دیتابیس

Migration فایلی است که تغییرات schema را ثبت می‌کند — به جای تغییر مستقیم دیتابیس، یک تاریخچه از تغییرات دارید که در هر محیط (dev, staging, prod) قابل اجراست:

terminal — migration commands
# ساخت یک migration جدید بر اساس تغییرات entity npx typeorm migration:generate -d data-source.ts migrations/AddAgeToUsers # اجرای migrationهای در انتظار npx typeorm migration:run -d data-source.ts # برگرداندن آخرین migration npx typeorm migration:revert -d data-source.ts
💡

synchronize: false در production! اگر synchronize=true باشد، TypeORM خودکار schema را با entityها sync می‌کند — در development راحت است ولی در production خطرناک است (ممکن است داده از دست برود). همیشه از migration استفاده کنید.

نکات کلیدی برای مصاحبه

  • Entity معادل جدول است — با decorator مثل @Entity، @Column تعریف می‌شود.
  • Repository ابزار CRUD برای یک Entity خاص — getRepository(User).
  • relations در find() معادل JOIN/populate — رابطه‌ها را خودکار لود می‌کند.
  • QueryBuilder برای query‌های پیچیده که Repository ساده کافی نیست.
  • Migration تغییرات schema را ثبت می‌کند — در production همیشه از این استفاده کنید، نه synchronize.
  • @OneToMany، @ManyToOne، @ManyToMany روابط بین جداول را مثل SQL foreign key تعریف می‌کنند.
  • سوال رایج: «چرا synchronize:true در production خطرناک است؟» — TypeORM خودکار schema دیتابیس را با Entityها هماهنگ می‌کند، حتی اگر یعنی حذف یک ستون یا جدول؛ این می‌تواند بدون هشدار داده واقعی را از بین ببرد.
  • یک تله رایج: فراموش کردن اجرای migration بعد از تغییر یک Entity — دیتابیس واقعی هنوز ساختار قدیمی را دارد و کد با آن ناسازگار می‌شود.
  • ORM (مثل TypeORM) کار با دیتابیس را شیء‌گرا می‌کند اما هزینه‌اش این است که گاهی query تولیدشده بهینه نیست — برای query‌های حساس به performance، QueryBuilder یا SQL خام بهتر است.
  • در TypeORM، تغییر یک Entity به‌تنهایی دیتابیس واقعی را عوض نمی‌کند — باید حتماً یک migration جدید بسازید و اجرا کنید.
