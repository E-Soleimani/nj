چطور داده را با اصول برنامه‌نویسی تابعی مدل کنیم — توابع خالص، immutability، و الگوهایی که خطاهای null/undefined را از بین می‌برند.

Functional Data Modeling چیست؟

در برنامه‌نویسی تابعی، به جای کلاس‌ها و mutation، داده را با ساختارهای immutable و توابع خالص (pure functions) مدل می‌کنیم. این رویکرد باگ‌های مرتبط با mutation ناخواسته را از بین می‌برد و کد را قابل‌پیش‌بینی‌تر می‌کند.

Pure Function — تابع خالص

تابع خالص دو ویژگی دارد: همیشه برای ورودی یکسان، خروجی یکسان می‌دهد و هیچ side effect ندارد:

pure-vs-impure.js
// ❌ Impure — به متغیر خارجی وابسته و آن را تغییر می‌دهد let total = 0; function addToTotal(amount) { total += amount; // side effect — متغیر خارجی را تغییر می‌دهد return total; } // ❌ Impure — به Date.now() وابسته (هر بار نتیجه فرق دارد) function createOrder(items) { return { items, createdAt: Date.now() }; } // ✅ Pure — فقط به ورودی وابسته، هیچ چیز خارجی را تغییر نمی‌دهد function calculateTotal(items) { return items.reduce((sum, item) => sum + item.price * item.qty, 0); } // ✅ Pure — تاریخ به عنوان پارامتر داده می‌شود، نه گرفته‌شده از سیستم function createOrderPure(items, timestamp) { return { items, createdAt: timestamp }; }

چرا توابع خالص مهم‌اند؟ تست‌نویسی راحت‌تر می‌شود (بدون mock کردن چیزی)، debugging ساده‌تر می‌شود (نتیجه فقط به ورودی بستگی دارد)، و کد در محیط‌های concurrent امن‌تر است.

Immutability — عدم تغییر داده

به جای تغییر مستقیم یک object یا array، یک نسخه جدید با تغییرات می‌سازیم. این از باگ‌های ناشی از reference های مشترک جلوگیری می‌کند:

immutability.js
// ❌ Mutation — object اصلی تغییر می‌کند function addItemMutable(cart, item) { cart.items.push(item); // cart اصلی را تغییر می‌دهد! return cart; } const cart1 = { items: [] }; const cart2 = addItemMutable(cart1, { name: 'Book' }); console.log(cart1 === cart2); // true — همان object است! باگ‌خطر // ✅ Immutable — یک object جدید ساخته می‌شود function addItemImmutable(cart, item) { return { ...cart, items: [...cart.items, item] // آرایه جدید با spread }; } const cart3 = { items: [] }; const cart4 = addItemImmutable(cart3, { name: 'Book' }); console.log(cart3 === cart4); // false — دو object جدا console.log(cart3.items.length); // 0 — اصلی دست نخورده باقی ماند // Object.freeze — جلوگیری از mutation در runtime const config = Object.freeze({ apiUrl: 'https://api.example.com' }); // config.apiUrl = 'hacked'; ← در strict mode خطا می‌دهد، در غیر آن silently fail

مدل‌سازی داده با Algebraic Data Types

به جای استفاده از null یا flagهای boolean پراکنده، داده را با ساختارهایی مدل می‌کنیم که همه حالت‌های ممکن را صریح نشان دهند. این الگو خطاهای null/undefined را از بین می‌برد:

result-pattern.js — Result Type
// به جای throw/catch یا null، یک نوع Result می‌سازیم // که هر دو حالت موفقیت و خطا را صریح نشان می‌دهد function Ok(value) { return { success: true, value }; } function Err(error) { return { success: false, error }; } // تابعی که هیچ‌وقت throw نمی‌کند — همیشه یک Result برمی‌گرداند function parseUserAge(input) { const age = Number(input); if (Number.isNaN(age)) { return Err('سن باید عدد باشد'); } if (age < 0 || age > 120) { return Err('سن نامعتبر است'); } return Ok(age); } // استفاده — caller مجبور است هر دو حالت را در نظر بگیرد const result = parseUserAge('25'); if (result.success) { console.log('سن معتبر:', result.value); } else { console.error('خطا:', result.error); } // مزیت بزرگ — کامپایلر TypeScript مجبورتان می‌کند هر دو حالت را چک کنید // (در فصل TypeScript بیشتر می‌بینیم)

Discriminated Union — یکی از چند حالت ممکن

order-states.js
// به جای یک object با فیلدهای مبهم (status, paid, shipped, ...) // هر حالت سفارش را به صورت صریح مدل می‌کنیم function PendingOrder(items) { return { type: 'pending', items }; } function PaidOrder(items, transactionId) { return { type: 'paid', items, transactionId }; } function ShippedOrder(items, transactionId, trackingNumber) { return { type: 'shipped', items, transactionId, trackingNumber }; } // پردازش بر اساس type — هیچ فیلد undefined مبهمی نیست function describeOrder(order) { switch (order.type) { case 'pending': return 'در انتظار پرداخت'; case 'paid': return `پرداخت شد: ${order.transactionId}`; case 'shipped': return `ارسال شد: ${order.trackingNumber}`; default: throw new Error('حالت ناشناخته'); } }

نکات کلیدی برای مصاحبه

  • Pure Function: هیچ side effect ندارد و برای ورودی یکسان، خروجی یکسان می‌دهد.
  • Immutability: به جای تغییر مستقیم، یک نسخه جدید با spread یا Object.freeze بسازید.
  • الگوی Result Type (Ok/Err) به جای throw/catch — خطا را صریح در نوع برگشتی نشان می‌دهد.
  • Discriminated Union برای مدل کردن حالت‌های مختلف یک entity — به جای فیلدهای boolean پراکنده.
  • این الگوها در TypeScript با Union Types خیلی قوی‌تر می‌شوند — کامپایلر همه حالت‌ها را چک می‌کند.
  • سوال رایج: «چرا Pure Function تست کردنش راحت‌تر است؟» — چون به هیچ چیز خارج از خودش وابسته نیست (نه database، نه متغیر global)؛ فقط با دادن ورودی و چک کردن خروجی می‌توان تستش کرد، بدون mock کردن چیزی.
  • یک تله رایج: فکر کردن Immutability یعنی کندی همیشگی — در عمل، برای اکثر برنامه‌ها این هزینه ناچیز است در مقابل کاهش باگ‌های ناشی از تغییر ناخواسته یک object مشترک.
  • مثال ساده Discriminated Union: به جای { status: 'ok', error: null } که حالت نامعتبر (status ok ولی error پر) اجازه می‌دهد، بنویسید { type: 'success' } | { type: 'error', message } که فقط یک حالت ممکن است.
  • در برنامه‌نویسی تابعی، از mutation روی آرایه (مثل push، splice) پرهیز می‌شود و به جایش از متدهایی مثل map و filter استفاده می‌شود که آرایه جدید برمی‌گردانند.
