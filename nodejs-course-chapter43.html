Onion &
Clean Architecture

معماری لایه‌ای که منطق تجاری را از جزئیات فنی (database, framework) جدا می‌کند — قابل تست‌تر، قابل تعویض‌تر، و مقیاس‌پذیرتر برای پروژه‌های بزرگ.

Onion ArchitectureClean ArchitectureDomain LayerUse Cases

مشکل معماری‌های ساده

در پروژه‌های ساده، معمولاً controller مستقیم به database وصل می‌شود. وقتی پروژه بزرگ می‌شود، این باعث می‌شود منطق تجاری (business logic) با جزئیات فنی (database, HTTP) قاطی شود — تغییر database یا framework خیلی سخت می‌شود. Onion Architecture و Clean Architecture این مشکل را حل می‌کنند.

Onion Architecture — لایه‌های متحدالمرکز

تصور کنید پروژه را مثل یک پیاز لایه‌لایه ببینید. لایه‌های داخلی (منطق تجاری اصلی) هیچ‌وقت نباید به لایه‌های بیرونی (database، framework) وابسته باشند — فقط برعکس.

قانون طلایی وابستگی: وابستگی‌ها همیشه به سمت داخل هستند — لایه بیرونی می‌تواند به داخلی وابسته باشد، ولی داخلی هیچ‌وقت نباید بداند لایه بیرونی چیست (Express، MongoDB، ...).

لایه‌های Onion Architecture

۱. Domain (مرکز)

Entityها و منطق تجاری خالص — هیچ وابستگی خارجی ندارد. فقط JavaScript/TypeScript خالص.

۲. Application (Use Cases)

orchestration منطق تجاری — چه کاری باید انجام شود. به interfaceها وابسته است نه implementation.

۳. Infrastructure

پیاده‌سازی واقعی — database، email service، پرداخت. اینجا implementation خاص است.

۴. Presentation (بیرونی‌ترین)

Controller، HTTP، GraphQL — نقطه ورود از بیرون به سیستم.

پیاده‌سازی عملی — یک ماژول کامل

لایه Domain — قلب سیستم

domain/entities/Order.ts
// هیچ import از framework یا database اینجا نیست! // فقط منطق تجاری خالص export class Order { private constructor( public readonly id: string, private items: OrderItem[], private status: OrderStatus ) {} static create(items: OrderItem[]): Order { if (items.length === 0) { throw new Error('سفارش باید حداقل یک آیتم داشته باشد'); } return new Order(generateId(), items, 'pending'); } calculateTotal(): number { // منطق تجاری خالص — قابل تست بدون هیچ mock return this.items.reduce((sum, item) => sum + item.price * item.qty, 0); } confirm(): void { if (this.status !== 'pending') { throw new Error('فقط سفارش pending قابل تایید است'); } this.status = 'confirmed'; } }

لایه Application — Use Case

application/use-cases/CreateOrder.ts
// interface — نه implementation. لایه Application به abstraction وابسته است export interface OrderRepository { save(order: Order): Promise<void>; findById(id: string): Promise<Order | null>; } export class CreateOrderUseCase { // وابسته به interface — نه به MongoDB یا Postgres خاص constructor(private orderRepo: OrderRepository) {} async execute(items: OrderItem[]): Promise<Order> { const order = Order.create(items); // منطق در Domain await this.orderRepo.save(order); return order; } }

لایه Infrastructure — پیاده‌سازی واقعی

infrastructure/repositories/MongoOrderRepository.ts
import { OrderRepository } from '../../application/use-cases/CreateOrder'; // اینجا از MongoDB استفاده می‌شود — جزئیات فنی export class MongoOrderRepository implements OrderRepository { constructor(private model: typeof OrderModel) {} async save(order: Order): Promise<void> { await this.model.create({ id: order.id, /* ... */ }); } async findById(id: string): Promise<Order | null> { const doc = await this.model.findOne({ id }); return doc ? mapToOrder(doc) : null; } } // اگر بخواهیم به PostgreSQL برویم، فقط این فایل عوض می‌شود // Domain و Application هیچ تغییری لازم ندارند!

لایه Presentation — Controller

presentation/controllers/OrderController.ts
@Controller('orders') export class OrderController { constructor(private createOrderUseCase: CreateOrderUseCase) {} @Post() async create(@Body() dto: CreateOrderDto) { // Controller فقط HTTP را به Use Case وصل می‌کند — منطقی اینجا نیست const order = await this.createOrderUseCase.execute(dto.items); return { id: order.id, total: order.calculateTotal() }; } }

چرا این معماری ارزش دارد؟

  • تست‌پذیری: منطق Domain بدون هیچ mock یا database واقعی تست می‌شود.
  • تعویض‌پذیری: تغییر از MongoDB به PostgreSQL فقط لایه Infrastructure را تحت تأثیر قرار می‌دهد.
  • خوانایی: منطق تجاری در یک جای مشخص است، نه پخش شده در controllerها.
⚠️

Over-engineering هشدار: این معماری برای پروژه‌های بزرگ و پیچیده ارزش دارد. برای یک CRUD ساده، این لایه‌بندی می‌تواند boilerplate اضافه بدون فایده واقعی باشد. تناسب پروژه را در نظر بگیرید.

نکات کلیدی برای مصاحبه

  • Onion/Clean Architecture: وابستگی‌ها همیشه به سمت مرکز (Domain) هستند، نه برعکس.
  • Domain Layer هیچ وابستگی خارجی ندارد — قابل تست بدون database یا framework واقعی.
  • Application Layer به interface وابسته است، نه implementation خاص — همان Dependency Inversion.
  • Infrastructure Layer جزئیات فنی (database, API خارجی) را پیاده‌سازی می‌کند.
  • این معماری همان اصول SOLID و DI است که در فصل‌های قبل دیدیم — فقط در مقیاس کل پروژه.
  • برای پروژه‌های کوچک ممکن است overkill باشد — انتخاب معماری باید متناسب با اندازه و طول عمر پروژه باشد.
  • سوال رایج: «فایده اصلی این معماری چیست؟» — اگر بخواهید MongoDB را با PostgreSQL عوض کنید، فقط لایه Infrastructure تغییر می‌کند؛ منطق تجاری اصلی (Domain) اصلاً دست نمی‌خورد.
  • یک تله رایج: قرار دادن منطق تجاری داخل Controller یا Repository — این باعث می‌شود منطق اصلی به یک framework یا دیتابیس خاص وابسته شود و تست کردنش سخت شود.
  • لایه‌بندی این معماری از داخل به بیرون: Domain (قلب سیستم) → Application (Use Caseها) → Infrastructure (پیاده‌سازی) → Presentation (ورودی HTTP/GraphQL).
  • Domain Entities باید بتوانند بدون هیچ import از Express، Mongoose یا هر framework دیگری کامپایل و تست شوند — این تست بودن معیار خوبی برای رعایت درست این معماری است.
