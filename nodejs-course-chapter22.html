Frameworks &
IOC / DI

Inversion of Control (IOC) و Dependency Injection (DI) دو مفهوم مهم در معماری نرم‌افزار هستند. این‌ها پایه‌ی framework‌هایی مثل NestJS هستند. درک این مفاهیم نشان می‌دهد که فقط یک کدنویس نیستید — معماری هم بلدید.

IoC Dependency Injection Decorators SOLID Testability

مشکل — Tight Coupling

وقتی یک class مستقیماً dependency‌هایش را می‌سازد، به آن‌ها وابسته (tightly coupled) می‌شود. این مشکل ساده است ولی در پروژه‌های بزرگ باعث کد ناتست‌پذیر و غیرقابل‌تغییر می‌شود:

❌ tight-coupling.js — مشکل‌دار
// UserService خودش UserRepository و EmailService می‌سازد class UserService { constructor() { // مشکل ۱: نمی‌توانیم برای تست Mock تزریق کنیم this.repo = new UserRepository(); // مشکل ۲: اگر بخواهیم EmailService را عوض کنیم، باید UserService تغییر کند this.email = new EmailService(); } async registerUser(name, email) { const user = await this.repo.create({ name, email }); await this.email.send(email, 'Welcome!'); return user; } } // در تست: نمی‌توانیم EmailService را mock کنیم // همیشه ایمیل واقعی ارسال می‌شود!

راه‌حل — Dependency Injection

Dependency Injection یعنی به جای اینکه class خودش dependency‌ها را بسازد، از بیرون به آن تزریق می‌شوند. کلاس فقط می‌گوید «به چه چیزی نیاز دارم» و یک سیستم خارجی آن را فراهم می‌کند.

✅ dependency-injection.js — درست
// UserService dependency‌ها را از بیرون می‌گیرد class UserService { constructor(userRepository, emailService) { // می‌گوییم «به این‌ها نیاز دارم» — نمی‌سازیم this.repo = userRepository; this.email = emailService; } async registerUser(name, email) { const user = await this.repo.create({ name, email }); await this.email.send(email, 'Welcome!'); return user; } } // در production — dependency واقعی تزریق می‌شود const userService = new UserService( new UserRepository(UserModel), new EmailService(smtpConfig) ); // در تست — mock تزریق می‌شود — ایمیل ارسال نمی‌شود const mockEmailService = { send: jest.fn().mockResolvedValue(true) }; const userServiceForTest = new UserService(mockRepo, mockEmailService);

IoC Container — اتوماسیون DI

در پروژه‌های بزرگ، دستی ساختن همه dependency‌ها خسته‌کننده است. IoC Container این کار را خودکار می‌کند. شما می‌گویید چه چیزی می‌خواهید، container درستش می‌کند و می‌دهد.

IoC یعنی چی؟ معمولاً شما dependency‌ها را کنترل می‌کنید. با IoC این کنترل به framework داده می‌شود — framework می‌سازد و می‌دهد. به همین دلیل می‌گویند «Inversion of Control» — کنترل وارونه شده.

ioc-container.js — ساده‌ترین container
// یک IoC Container ساده class Container { constructor() { this.bindings = new Map(); // نام → factory function this.singletons = new Map(); // cache برای singleton } // bind — ثبت می‌کنیم «چطور بسازیم» bind(name, factory) { this.bindings.set(name, factory); return this; } // make — می‌خواهیم instance بگیریم make(name) { if (this.singletons.has(name)) { return this.singletons.get(name); // از cache برگردان } const factory = this.bindings.get(name); if (!factory) throw new Error(`${name} registered نشده`); const instance = factory(this); // container خودش را پاس می‌دهد this.singletons.set(name, instance); return instance; } } // استفاده const container = new Container(); // Register کردن container .bind('userRepository', () => new UserRepository(UserModel)) .bind('emailService', () => new EmailService(smtpConfig)) .bind('userService', (c) => new UserService( c.make('userRepository'), c.make('emailService') )); // Resolve — container همه چیز را می‌سازد const userService = container.make('userService');

Decorators — IOC با TypeScript

در NestJS از Decorators برای تعریف DI استفاده می‌شود. Decorator یک تابع است که روی class یا method اعمال می‌شود و metadata اضافه می‌کند:

decorators-example.ts — پیش‌نمایش NestJS
// این سبک کدنویسی در NestJS استفاده می‌شود // @Injectable — این class می‌تواند inject شود @Injectable() class UserRepository { constructor(private readonly model: typeof User) {} async findById(id: string) { return this.model.findById(id); } } // @Injectable — UserService هم قابل inject است @Injectable() class UserService { // NestJS خودکار UserRepository را inject می‌کند constructor(private readonly userRepo: UserRepository) {} async getUser(id: string) { return this.userRepo.findById(id); } } // @Controller — این class یک HTTP controller است @Controller('/users') class UserController { // NestJS خودکار UserService را inject می‌کند constructor(private readonly userService: UserService) {} // @Get(':id') — این method به GET /users/:id جواب می‌دهد @Get(':id') async getUser(@Param('id') id: string) { return this.userService.getUser(id); } }

اصول SOLID

SOLID پنج اصل طراحی نرم‌افزار است که کد را نگهداری‌پذیر می‌کند. DI مستقیماً از آن‌ها می‌آید:

  • Single Responsibility — هر class فقط یک مسئولیت داشته باشد. UserService فقط user logic، نه ارسال ایمیل.
  • Open/Closed — برای گسترش باز، برای تغییر بسته. رفتار جدید با extend کردن اضافه شود.
  • Liskov Substitution — زیرکلاس باید جایگزین والدش شود بدون اینکه چیزی بشکند.
  • Interface Segregation — interface‌های کوچک و مشخص بهتر از یک interface بزرگ.
  • Dependency Inversion — به abstraction وابسته باشید نه implementation. (این همان DI است)

نکات کلیدی برای مصاحبه

  • DI: dependency‌ها از بیرون تزریق می‌شوند — نه داخل class ساخته می‌شوند. کد testable‌تر می‌شود.
  • IoC: کنترل ساخت object‌ها به framework داده می‌شود — به همین دلیل «وارونه» است.
  • Decorator: metadata به class اضافه می‌کند. NestJS از decorator برای DI استفاده می‌کند.
  • SOLID پنج اصل طراحی: Single Responsibility، Open/Closed، Liskov، Interface Segregation، Dependency Inversion.
  • تفاوت DI و IoC: DI یک روش است، IoC یک اصل. DI یک روش پیاده‌سازی IoC است.
  • سوال رایج: «DI چه مشکلی را حل می‌کند؟» — بدون DI، هر class خودش dependencyهایش را می‌سازد و برای تست باید همه آن‌ها واقعی اجرا شوند؛ با DI، در تست می‌توانید mock جایگزین کنید بدون تغییر کد اصلی.
  • یک تله رایج: فکر کردن که IoC Container فقط برای پروژه‌های بزرگ لازم است — حتی پروژه‌های کوچک هم از تزریق دستی dependency در constructor سود می‌برند، بدون نیاز به framework خاص.
  • Single Responsibility رایج‌ترین اصل SOLID در مصاحبه است: هر class باید فقط یک دلیل برای تغییر داشته باشد — مثلاً یک class نباید هم منطق تجاری و هم ارسال ایمیل را انجام دهد.
  • در JavaScript/TypeScript، DI معمولاً با پاس دادن dependency در constructor پیاده می‌شود؛ IoC Container (مثل NestJS) این کار را خودکار و بر اساس type انجام می‌دهد.
