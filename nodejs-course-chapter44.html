Microservices چیست؟

به جای یک اپلیکیشن بزرگ (Monolith)، سیستم را به چند سرویس کوچک و مستقل تقسیم می‌کنیم — هر سرویس یک دامنه مشخص دارد (users، orders، payments)، دیتابیس جدا دارد، و از طریق شبکه (HTTP، message queue) با هم ارتباط برقرار می‌کنند.

Monolith

یک codebase، یک deploy، یک دیتابیس

ساده برای شروع، سخت برای scale تیم بزرگ

Microservices

چند سرویس مستقل، deploy جدا، دیتابیس جدا

پیچیده‌تر، ولی هر تیم مستقل کار می‌کند

⚠️

هشدار مصاحبه رایج: Microservices همیشه بهترین انتخاب نیست! برای تیم‌های کوچک، Monolith اغلب سریع‌تر و ساده‌تر است. مصاحبه‌کننده می‌خواهد ببیند شما trade-offها را درک می‌کنید، نه اینکه فکر کنید microservices همیشه بهتر است.

الگوهای ارتباطی بین سرویس‌ها

Synchronous — HTTP/REST یا gRPC

یک سرویس مستقیم درخواست HTTP به سرویس دیگر می‌فرستد و منتظر پاسخ می‌ماند:

order-service.js
// Order Service مستقیم به User Service درخواست می‌زند async function createOrder(userId, items) { // خطر: اگر User Service پایین باشد، Order Service هم گیر می‌افتد! const user = await fetch(`http://user-service/users/${userId}`).then(r => r.json()); if (!user.isActive) throw new Error('کاربر غیرفعال است'); return saveOrder({ userId, items, userEmail: user.email }); } // بهتر است با Circuit Breaker (فصل 38) این ارتباط را محافظت کنید

Asynchronous — Event-Driven (پیشنهادی)

سرویس‌ها با انتشار رویداد ارتباط برقرار می‌کنند — بدون وابستگی مستقیم به آنلاین بودن سرویس دیگر:

event-driven-services.js
// Order Service — فقط رویداد منتشر می‌کند، منتظر کسی نمی‌ماند async function createOrder(userId, items) { const order = await saveOrder({ userId, items }); // انتشار رویداد — نمی‌داند چه کسی گوش می‌دهد await messageQueue.publish('order.created', { orderId: order.id, userId, total: order.total }); return order; // فوراً برمی‌گردد — منتظر Email/Inventory Service نمی‌ماند } // Email Service — مستقل گوش می‌دهد messageQueue.subscribe('order.created', async (event) => { await emailService.sendOrderConfirmation(event.userId, event.orderId); }); // Inventory Service — مستقل گوش می‌دهد messageQueue.subscribe('order.created', async (event) => { await inventoryService.reserveStock(event.orderId); });

Saga Pattern — Transaction توزیع‌شده

در Monolith، یک Database Transaction همه چیز را یکجا rollback می‌کند. در microservices این ممکن نیست چون هر سرویس دیتابیس جدا دارد. Saga Pattern با یک زنجیره از event و compensating action (عملیات جبرانی) این مشکل را حل می‌کند:

saga-pattern.js
// سناریو: سفارش → کسر موجودی → پرداخت → ارسال // اگر پرداخت fail شود، باید موجودی برگردد (compensating action) class OrderSaga { async execute(order) { const completedSteps = []; try { await this.reserveInventory(order); completedSteps.push('inventory'); await this.chargePayment(order); completedSteps.push('payment'); await this.scheduleShipping(order); completedSteps.push('shipping'); } catch (error) { // اگر یک مرحله fail شود، مراحل قبلی را جبران کن (به ترتیب معکوس) console.error('Saga fail شد — در حال جبران...'); await this.compensate(completedSteps, order); throw error; } } async compensate(completedSteps, order) { if (completedSteps.includes('payment')) { await this.refundPayment(order); // عملیات جبرانی } if (completedSteps.includes('inventory')) { await this.releaseInventory(order); // موجودی برگردد } } }

Molecular و Seneca — فریمورک‌های میکروسرویس Node.js

برخلاف NestJS که کل framework است، Molecular و Seneca مخصوص ساخت microservices در Node.js طراحی شده‌اند — با discovery، load balancing و ارتباط داخلی خودکار.

seneca-example.js
const seneca = require('seneca')(); // تعریف یک "action" — معادل یک endpoint در سرویس seneca.add('role:user,cmd:get', async function(msg) { const user = await db.findUser(msg.id); return { user }; }); // یک سرویس دیگر — بدون دانستن آدرس دقیق سرویس — پیام می‌فرستد seneca.act('role:user,cmd:get', { id: '123' }, (err, result) => { console.log(result.user); }); // Seneca خودکار discovery و load balancing انجام می‌دهد // بدون نیاز به hard-code آدرس هر سرویس
💡

واقعیت صنعتی: امروزه بیشتر تیم‌ها به جای Seneca/Molecular، از NestJS با built-in microservices transport (TCP, Redis, Kafka, gRPC) یا Kubernetes با service mesh استفاده می‌کنند. Seneca همچنان یک ابزار خوب برای یادگیری مفاهیم است.

نکات کلیدی برای مصاحبه

  • Microservices همیشه بهترین انتخاب نیست — برای تیم کوچک، Monolith اغلب بهتر است.
  • Synchronous (HTTP) ساده ولی سرویس‌ها را به هم وابسته می‌کند — نیاز به Circuit Breaker دارد.
  • Asynchronous (Event-Driven) decoupling بهتری می‌دهد — سرویس‌ها مستقل عمل می‌کنند.
  • Saga Pattern برای transaction توزیع‌شده — به جای rollback واحد، عملیات جبرانی (compensating action) استفاده می‌شود.
  • هر microservice باید دیتابیس مستقل داشته باشد — اشتراک دیتابیس بین سرویس‌ها ضد الگو است.
  • Molecular/Seneca فریمورک‌های تخصصی microservices در Node.js هستند — امروزه NestJS با built-in transport هم رایج است.
  • سوال رایج: «چرا هر microservice باید دیتابیس مستقل داشته باشد؟» — اگر دو سرویس یک دیتابیس مشترک داشته باشند، تغییر schema توسط یک تیم می‌تواند سرویس تیم دیگر را بدون اطلاع بشکند؛ این دقیقاً همان مشکلی است که microservices قرار بود حل کند.
  • یک تله رایج: شروع یک پروژه جدید مستقیم با معماری microservices «چون همه بزرگ‌ها این کار را می‌کنند» — معمولاً بهتر است با یک Monolith خوش‌ساخت شروع کرد و بعد در صورت نیاز واقعی، تدریجی جدا کرد.
  • API Gateway نقطه ورود واحد برای همه microservices است — درخواست کلاینت را به سرویس درست مسیریابی می‌کند و کارهایی مثل authentication را متمرکز انجام می‌دهد.
  • در Saga Pattern، اگر یک مرحله fail شود، مراحل قبلی با اجرای عملیات جبرانی (مثل بازگرداندن پول یا آزاد کردن موجودی) به ترتیب معکوس لغو می‌شوند — چون نمی‌توان یک transaction واحد روی چند دیتابیس مستقل داشت.
