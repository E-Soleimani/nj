Cron &
Scheduled Tasks

اجرای کارهای زمان‌بندی‌شده در Node.js — از node-cron ساده تا حل مشکل duplicate execution در چند instance با Distributed Lock و Agenda.

node-cronAgendaDistributed Lock

چرا Scheduled Task لازم است؟

خیلی از کارها نباید منتظر درخواست کاربر بمانند — پاک‌سازی داده‌های قدیمی هر شب، ارسال گزارش هفتگی، sync با یک API خارجی هر ساعت. این‌ها Cron Job یا Scheduled Task نام دارند.

node-cron — ساده‌ترین راه

terminal
npm install node-cron
jobs/cleanup.js
const cron = require('node-cron'); // فرمت Cron: دقیقه ساعت روزماه ماه روزهفته // * * * * * = هر دقیقه // هر روز ساعت 3 بامداد — پاک‌سازی logهای قدیمی cron.schedule('0 3 * * *', async () => { console.log('شروع پاک‌سازی logهای قدیمی...'); await Log.deleteMany({ createdAt: { $lt: new Date(Date.now() - 30 * 24 * 60 * 60 * 1000) } }); }); // هر دوشنبه ساعت 9 صبح — گزارش هفتگی cron.schedule('0 9 * * 1', async () => { const report = await generateWeeklyReport(); await emailService.send('admin@company.com', report); }); // هر 15 دقیقه — sync با API خارجی cron.schedule('*/15 * * * *', async () => { await syncExternalInventory(); });

خوانایی فرمت Cron: پنج ستاره از راست به چپ: روز هفته (0-6)، ماه (1-12)، روز ماه (1-31)، ساعت (0-23)، دقیقه (0-59). * یعنی «هر مقدار». */15 یعنی «هر 15 واحد». سایت crontab.guru برای تست فرمت‌ها مفید است.

مشکل بزرگ: چند Instance، چند بار اجرا!

یادتان هست از فصل PM2 و Cluster؟ اگر برنامه با ۴ instance اجرا شود، node-cron در هر ۴ تا به صورت مستقل اجرا می‌شود — یعنی همان job چهار بار اجرا می‌شود! این باعث می‌شود گزارش ۴ بار فرستاده شود یا پردازش تکراری رخ دهد.

distributed-lock-cron.js
const cron = require('node-cron'); const redis = require('../config/redis'); // راه‌حل: Distributed Lock با Redis // فقط instanceی که موفق به گرفتن lock شود، job را اجرا می‌کند async function runWithLock(lockKey, ttlSeconds, task) { // SET با NX (فقط اگر وجود نداشت) و EX (با انقضا) const acquired = await redis.set(lockKey, 'locked', 'EX', ttlSeconds, 'NX'); if (!acquired) { console.log('Lock توسط instance دیگری گرفته شده — رد شدن'); return; } try { await task(); } finally { await redis.del(lockKey); // آزاد کردن lock بعد از اتمام } } cron.schedule('0 3 * * *', () => { runWithLock('lock:daily-cleanup', 300, async () => { // حتی اگر 4 instance این را اجرا کنند، فقط یکی واقعاً کار می‌کند await Log.deleteMany({ /* ... */ }); }); });

Agenda — راه‌حل حرفه‌ای‌تر (Persistent Jobs)

node-cron در حافظه است — اگر سرور restart شود، برنامه‌ریزی از دست می‌رود. Agenda jobها را در MongoDB ذخیره می‌کند — پایدار، قابل query، و به صورت built-in مشکل چند-instance را حل می‌کند:

agenda-example.js
const Agenda = require('agenda'); // npm install agenda const agenda = new Agenda({ db: { address: process.env.DATABASE_URL } }); // تعریف job agenda.define('send-welcome-email', async (job) => { const { userId } = job.attrs.data; await emailService.sendWelcome(userId); }); // job یکبار در آینده — مثلاً 1 ساعت بعد از ثبت‌نام await agenda.schedule('in 1 hour', 'send-welcome-email', { userId: '123' }); // job تکرارشونده — مثل cron ولی persistent در دیتابیس await agenda.every('1 day', 'daily-report'); // Agenda خودکار مطمئن می‌شود فقط یک worker هر job را می‌گیرد // (با mechanism داخلی lock در دیتابیس) await agenda.start();

نکات کلیدی برای مصاحبه

  • node-cron ساده و سریع است ولی in-memory — با چند instance، job تکراری اجرا می‌شود.
  • راه‌حل مشکل چند-instance: Distributed Lock با Redis (SET NX EX).
  • Agenda jobها را در دیتابیس ذخیره می‌کند — persistent، قابل query، و مشکل duplicate را حل می‌کند.
  • فرمت Cron: دقیقه ساعت روزماه ماه روزهفته — همیشه با ابزاری مثل crontab.guru تست کنید.
  • برای jobهای یکبار در آینده (نه تکرارشونده)، Agenda's schedule() مناسب‌تر از cron است.
  • در معماری microservices، بهتر است یک سرویس مجزا مسئول scheduled taskها باشد — نه در همان API server.
  • سوال رایج: «چرا با چند instance، همان cron job چند بار اجرا می‌شود؟» — هر instance کد یکسانی دارد و node-cron در حافظه هر process جدا اجرا می‌شود؛ سرور نمی‌داند instanceهای دیگر هم همین job را دارند، پس هر کدام مستقل اجرا می‌کند.
  • یک تله رایج: فراموش کردن timezone در تنظیم cron — اگر سرور روی UTC باشد ولی انتظار اجرا در ساعت محلی دارید، job در ساعت اشتباه اجرا می‌شود.
  • Distributed Lock با دستور Redis SET key value NX EX ttl کار می‌کند: NX یعنی فقط اگر key وجود نداشت ست شود؛ یعنی فقط اولین instance که این دستور را بزند «قفل» را می‌گیرد، بقیه رد می‌شوند.
  • برای jobهای حیاتی (مثل صدور فاکتور ماهانه)، باید علاوه بر اجرای موفق، یک مکانیزم alert هم داشته باشید که اگر job اجرا نشد یا fail شد، تیم مطلع شود.
