فراتر از Unit Test ساده

در فصل ۸ با Jest و TDD آشنا شدیم. Unit Testهای ساده کافی نیستند — باید مطمئن شوید سیستم با dependency‌های واقعی (database, API خارجی) هم درست کار می‌کند. این فصل سه سطح تست پیشرفته‌تر را پوشش می‌دهد.

هرم تست — یادآوری سریع

Unit Tests (پایه هرم)

سریع، تعداد زیاد، تست یک تابع/کلاس ایزوله با mock

Integration Tests (میانه)

چند component با هم — با database واقعی (نه mock)

و در بالای هرم: E2E Tests — کل سیستم مثل کاربر واقعی.

Integration Test با Testcontainers

مشکل رایج: اگر database را mock کنید، ممکن است query واقعی اشتباه باشد ولی تست پاس شود. Testcontainers یک database واقعی (در Docker) فقط برای مدت تست اجرا می‌کند:

terminal
npm install --save-dev testcontainers
tests/user.integration.test.js
const { GenericContainer } = require('testcontainers'); const mongoose = require('mongoose'); describe('User Integration Tests', () => { let container; // قبل از همه تست‌ها — یک MongoDB واقعی در Docker بالا بیاور beforeAll(async () => { container = await new GenericContainer('mongo:7') .withExposedPorts(27017) .start(); const uri = `mongodb://${container.getHost()}:${container.getMappedPort(27017)}/test`; await mongoose.connect(uri); }, 30000); // timeout بیشتر — دانلود و راه‌اندازی container زمان می‌برد afterAll(async () => { await mongoose.disconnect(); await container.stop(); }); it('باید کاربر را در database واقعی ذخیره کند', async () => { const user = await User.create({ name: 'Ali', email: 'ali@test.com' }); // بدون mock — واقعاً از دیتابیس می‌خواند const found = await User.findById(user._id); expect(found.email).toBe('ali@test.com'); }); });

چرا Testcontainers بهتر از mock است؟ Mock فقط فرض می‌کند دیتابیس چطور رفتار می‌کند — اگر query شما واقعاً اشتباه SQL/Mongo باشد، mock متوجه نمی‌شود. با database واقعی، باگ‌های واقعی پیدا می‌شوند.

Contract Testing — بین Microservices

وقتی چند تیم روی سرویس‌های مختلف کار می‌کنند، چطور مطمئن شویم Order Service که به User Service وابسته است، بعد از تغییر User Service نمی‌شکند؟ Contract Testing (با ابزاری مثل Pact) یک قرارداد بین consumer و provider تعریف می‌کند:

contract-test-concept.js
// Consumer (Order Service) تعریف می‌کند چه چیزی از User Service انتظار دارد const contract = { request: { method: 'GET', path: '/users/123' }, response: { status: 200, body: { id: like('123'), // نوع string، مقدار دقیق مهم نیست email: like('test@test.com'), isActive: like(true) } } }; // این contract هم روی Consumer تست می‌شود (آیا request را درست می‌فرستد) // هم روی Provider تست می‌شود (آیا واقعاً این shape را برمی‌گرداند) // اگر User Service ساختار پاسخش را عوض کند، contract test در CI fail می‌شود // قبل از اینکه به production برسد و Order Service را بشکند

E2E Testing با Playwright/Supertest

برای API، Supertest امکان تست کامل HTTP request/response را بدون نیاز به سرور واقعی جدا می‌دهد:

tests/api.e2e.test.js
const request = require('supertest'); // npm install --save-dev supertest const app = require('../app'); describe('POST /api/orders', () => { it('باید سفارش جدید بسازد و آن را در پاسخ برگرداند', async () => { // لاگین اول — گرفتن token واقعی const loginRes = await request(app) .post('/auth/login') .send({ email: 'test@test.com', password: 'password123' }); const token = loginRes.body.accessToken; // حالا با token واقعی، endpoint اصلی را تست کن const res = await request(app) .post('/api/orders') .set('Authorization', `Bearer ${token}`) .send({ items: [{ productId: '1', qty: 2 }] }); expect(res.status).toBe(201); expect(res.body.data).toHaveProperty('id'); }); });

نکات کلیدی برای مصاحبه

  • Testcontainers: database واقعی در Docker فقط برای مدت تست — باگ‌های واقعی query را پیدا می‌کند.
  • Contract Testing (Pact) بین microservices جلوی شکستن API بدون اطلاع تیم دیگر را می‌گیرد.
  • Supertest برای تست کامل HTTP بدون نیاز به سرور جداگانه — درخواست مستقیم به app instance.
  • هرم تست: Unit (زیاد و سریع) → Integration (متوسط) → E2E (کم و کند ولی جامع).
  • Integration test با database واقعی، اعتماد بیشتری از mock می‌دهد ولی کندتر است — تعادل لازم است.
  • سوال رایج: «چرا mock کردن دیتابیس کافی نیست؟» — mock فقط فرض می‌کند دیتابیس چطور رفتار می‌کند؛ اگر query واقعی شما اشتباه SQL/Mongo باشد، mock هیچ‌وقت این باگ را نشان نمی‌دهد چون خودش هوشمند نیست، فقط جواب از پیش تعیین‌شده می‌دهد.
  • یک تله رایج: نوشتن فقط Unit Test و فکر کردن که همه چیز پوشش داده شده — Unit Testها با mock هستند و تعامل واقعی بین سرویس و دیتابیس/سرویس‌های دیگر را تست نمی‌کنند.
  • Contract Testing با دو طرف کار می‌کند: Consumer (سرویسی که درخواست می‌زند) و Provider (سرویسی که جواب می‌دهد)؛ هر دو طرف نسبت به یک قرارداد مشترک تست می‌شوند تا تغییرات ناسازگار زودتر مشخص شود.
  • Testهای E2E معمولاً کندترین و شکننده‌ترین‌اند (چون کل سیستم را نیاز دارند)، پس باید فقط برای مسیرهای حیاتی (مثل ثبت‌نام، پرداخت) استفاده شوند، نه هر جزئیات.
