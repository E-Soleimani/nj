Security
Essentials

آسیب‌پذیری‌های رایج در API‌های Node.js و راه دفاع از هرکدام — Helmet، CORS، Rate Limiting، XSS و NoSQL Injection.

HelmetCORSRate LimitingXSSInjection

چرا Security یک فصل جدا لازم دارد؟

امنیت یکی از موضوعاتی است که تا وقتی مشکلی پیش نیاید، نادیده گرفته می‌شود. در این فصل مهم‌ترین آسیب‌پذیری‌های رایج در Node.js/Express API‌ها و راه دفاع از هرکدام را می‌بینیم — موضوعاتی که تقریباً همیشه در مصاحبه‌های سطح متوسط به بالا پرسیده می‌شوند.

Helmet — Security Headers خودکار

مرورگرها رفتار خود را بر اساس HTTP headers تنظیم می‌کنند. Helmet مجموعه‌ای از headerهای امنیتی را خودکار تنظیم می‌کند:

terminal
npm install helmet
app.js
const helmet = require('helmet'); app.use(helmet()); // این یک خط، چندین header امنیتی تنظیم می‌کند: // X-Content-Type-Options: nosniff → جلوگیری از MIME sniffing // X-Frame-Options: DENY → جلوگیری از clickjacking // Strict-Transport-Security → اجبار HTTPS // Content-Security-Policy → محدود کردن منابع قابل بارگذاری // و چند header دیگر

CORS — دقیق و امن

CORS (Cross-Origin Resource Sharing) کنترل می‌کند کدام دامنه‌ها می‌توانند به API شما درخواست بزنند. تنظیم اشتباه، یا امنیت را می‌شکند یا کلاینت شما را قطع می‌کند.

cors-config.js
const cors = require('cors'); // ❌ خطرناک — همه دامنه‌ها اجازه دارند app.use(cors()); // origin: '*' پیش‌فرض // ✅ درست — فقط دامنه‌های مشخص const allowedOrigins = ['https://myapp.com', 'https://admin.myapp.com']; app.use(cors({ origin: (origin, callback) => { if (!origin || allowedOrigins.includes(origin)) { callback(null, true); } else { callback(new Error('دسترسی CORS رد شد')); } }, credentials: true, // اگر cookie/auth header لازم است methods: ['GET', 'POST', 'PUT', 'DELETE'] }));

Rate Limiting — جلوگیری از سوء استفاده

یادآوری از فصل ۲۱ (Redis) — همیشه روی endpoints حساس (login, signup) rate limit بگذارید:

rate-limit-express.js
const rateLimit = require('express-rate-limit'); // محدودیت عمومی const generalLimiter = rateLimit({ windowMs: 15 * 60 * 1000, // 15 دقیقه max: 100 // هر IP حداکثر 100 درخواست }); app.use(generalLimiter); // محدودیت سخت‌گیرانه‌تر برای login — جلوگیری از brute-force const loginLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 5, // فقط 5 تلاش لاگین در 15 دقیقه message: 'تعداد تلاش‌های لاگین بیش از حد مجاز — کمی صبر کنید' }); app.post('/auth/login', loginLimiter, loginHandler);

XSS — Cross-Site Scripting

وقتی داده ورودی کاربر بدون sanitize به HTML تزریق می‌شود، مهاجم می‌تواند اسکریپت مخرب اجرا کند:

xss-prevention.js
// ❌ خطرناک — کاربر می‌تواند <script> تزریق کند // input: "<script>steal_cookies()</script>" // ✅ همیشه ورودی کاربر را sanitize کنید const sanitizeHtml = require('sanitize-html'); function sanitizeUserInput(input) { return sanitizeHtml(input, { allowedTags: [], // هیچ HTML tag مجاز نیست allowedAttributes: {} }); } // همچنین در React/frontend، از dangerouslySetInnerHTML اجتناب کنید // React خودکار escape می‌کند مگر مجبورش کنید نکند

SQL/NoSQL Injection

یادآوری از فصل ۳۹ — همیشه parameterized query استفاده کنید. برای MongoDB هم خطر مشابه وجود دارد:

nosql-injection.js
// ❌ خطرناک — اگر req.body.email یک object باشد نه string // مثلاً: { "$gt": "" } — همه کاربران را برمی‌گرداند! User.findOne({ email: req.body.email, password: req.body.password }); // ✅ اعتبارسنجی نوع داده قبل از query (با Zod از فصل 27) const LoginSchema = z.object({ email: z.string().email(), // اگر object باشد، parse خطا می‌دهد password: z.string() }); const { email, password } = LoginSchema.parse(req.body); // نصب express-mongo-sanitize هم برای لایه دفاعی اضافه توصیه می‌شود npm install express-mongo-sanitize

نکات کلیدی برای مصاحبه

  • Helmet مجموعه‌ای از security headers را با یک خط تنظیم می‌کند.
  • CORS باید دقیق تنظیم شود — origin: '*' در production خطرناک است.
  • Rate Limiting روی endpoints حساس (login, signup, forgot-password) اجباری است.
  • XSS: هرگز HTML خام کاربر را بدون sanitize رندر نکنید.
  • NoSQL Injection هم واقعی است — همیشه نوع داده ورودی را با Zod/Joi اعتبارسنجی کنید.
  • Secretها هیچ‌وقت در کد یا Git نباشند — استفاده از Environment Variables و secret managerها.
  • سوال رایج: «CORS دقیقاً چه چیزی را کنترل می‌کند؟» — CORS محدودیت مرورگر است، نه امنیت سرور واقعی؛ فقط تعیین می‌کند کدام دامنه‌ها اجازه دارند از طریق مرورگر به API شما درخواست بزنند، ولی درخواست مستقیم (مثلاً از Postman) را نمی‌بندد.
  • یک تله رایج: فکر کردن CORS به‌تنهایی امنیت است — CORS جلوی حمله واقعی (مثل درخواست مستقیم به API با ابزار) را نمی‌گیرد؛ باید همراه با authentication واقعی استفاده شود.
  • CSRF (Cross-Site Request Forgery) وقتی خطرناک است که از cookie برای احراز هویت استفاده می‌کنید — با JWT در header (نه cookie) این حمله عملاً بی‌اثر می‌شود.
  • Rate Limiting نه‌تنها جلوی brute-force را می‌گیرد، بلکه از هزینه بالای API خارجی (مثل سرویس پیامک) در برابر سوءاستفاده هم محافظت می‌کند.
