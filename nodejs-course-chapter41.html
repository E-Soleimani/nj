Thinking in Types — یک تغییر ذهنیت

در فصل ۱۲ مبانی TypeScript را دیدیم. این فصل درباره چیز متفاوتی است: چطور با types فکر کنید — نه فقط syntax، بلکه استفاده از سیستم تایپ برای جلوگیری از حالت‌های نامعتبر در سطح کامپایلر، قبل از اینکه برنامه اجرا شود.

فلسفه اصلی: "Make illegal states unrepresentable" — طوری type بسازید که اصلاً نتوان یک حالت نامعتبر را نمایش داد. اگر نمی‌توانید بنویسیدش، نمی‌توانید باگش کنید.

مثال ۱ — به جای Boolean پرچم، Union Type

bad-vs-good-types.ts
// ❌ حالت نامعتبر قابل نمایش است interface Request { isLoading: boolean; data: any | null; error: string | null; } // این اجازه می‌دهد: { isLoading: true, data: {...}, error: 'خطا' } // هم loading، هم data، هم error همزمان — بی‌معنی و غیرممکن در واقعیت! // ✅ فقط یکی از این سه حالت ممکن است — کامپایلر تضمین می‌کند type RequestState = | { status: 'idle' } | { status: 'loading' } | { status: 'success'; data: any } | { status: 'error'; error: string }; function renderState(state: RequestState) { switch (state.status) { case 'idle': return 'شروع نشده'; case 'loading': return 'در حال بارگذاری...'; case 'success': return state.data; // اینجا TS می‌داند data وجود دارد case 'error': return state.error; // اینجا TS می‌داند error وجود دارد } } // امکان نداشتن error در حالت success وجود ندارد — کامپایلر جلویش را می‌گیرد

مثال ۲ — Branded Types — جلوگیری از اشتباه واحد

مشکل رایج: function transfer(fromId: string, toId: string, amount: number) — چه چیزی جلوی جابجایی fromId و toId را می‌گیرد؟ هیچی! هر دو string هستند. راه‌حل: Branded Types — یک type را با یک "برچسب" جعلی متمایز کنید:

branded-types.ts
// یک brand جعلی که فقط در compile-time وجود دارد type UserId = string & { readonly __brand: 'UserId' }; type OrderId = string & { readonly __brand: 'OrderId' }; // توابع تبدیل — تنها راه ساخت این typeها function toUserId(id: string): UserId { return id as UserId; } function toOrderId(id: string): OrderId { return id as OrderId; } function getUser(id: UserId) { /* ... */ } const userId = toUserId('user-123'); const orderId = toOrderId('order-456'); getUser(userId); // ✅ درست // getUser(orderId); ← Error! هرچند هر دو string هستند // TypeScript جلوی این اشتباه رایج را می‌گیرد

مثال ۳ — Generics برای کد قابل استفاده مجدد

generic-api-response.ts
// یک نوع عمومی برای همه پاسخ‌های API interface ApiResponse<T> { success: boolean; data?: T; error?: string; } // استفاده — T مشخص می‌کند شکل data چیست async function fetchUser(id: string): Promise<ApiResponse<User>> { // ... } async function fetchOrders(): Promise<ApiResponse<Order[]>> { // ... } // Generic constraint — T باید یک ویژگی خاص داشته باشد interface HasId { id: string | number; } function findById<T extends HasId>(items: T[], id: T['id']): T | undefined { return items.find(item => item.id === id); }

مثال ۴ — Mapped Types و Conditional Types

advanced-types.ts
// Mapped Type — ساخت type جدید از type موجود type Nullable<T> = { [K in keyof T]: T[K] | null }; interface User { name: string; age: number; } type NullableUser = Nullable<User>; // { name: string | null; age: number | null; } // Conditional Type — type بر اساس شرط type IsString<T> = T extends string ? 'yes' : 'no'; type A = IsString<string>; // 'yes' type B = IsString<number>; // 'no' // کاربرد واقعی — استخراج نوع Promise type Awaited2<T> = T extends Promise<infer U> ? U : T; type Result = Awaited2<Promise<string>>; // string

نکات کلیدی برای مصاحبه

  • فلسفه اصلی: «Make illegal states unrepresentable» — طراحی type که حالت نامعتبر را اصلاً اجازه ندهد.
  • Discriminated Union بهتر از چند فیلد boolean/nullable مستقل — کامپایلر همه حالت‌ها را می‌شناسد.
  • Branded Types برای جلوگیری از اشتباه دو مقدار هم‌نوع (مثل UserId و OrderId).
  • Generics کد را قابل استفاده مجدد می‌کنند بدون از دست دادن type safety.
  • Mapped/Conditional Types برای ساخت typeهای جدید از typeهای موجود — ابزار پیشرفته اما قدرتمند.
  • هدف نهایی: هر چه خطا زودتر (در compile-time) پیدا شود، هزینه رفعش کمتر است.
  • سوال رایج: «چرا Discriminated Union بهتر از چند فیلد nullable است؟» — با فیلدهای جدا (مثل data و error هر دو nullable)، حالت‌های بی‌معنی هم قابل نوشتن‌اند (هر دو پر یا هر دو خالی)؛ با Union، کامپایلر فقط اجازه یکی از حالت‌های تعریف‌شده را می‌دهد.
  • یک تله رایج: استفاده زیاد از any برای «رد شدن سریع از خطای کامپایلر» — این کار همه مزایای TypeScript را از بین می‌برد؛ به جای آن از unknown یا type دقیق‌تر استفاده کنید.
  • Generic Constraint (مثل <T extends HasId>) به شما اجازه می‌دهد یک تابع عمومی بنویسید ولی همچنان مطمئن باشید T حداقل یک ویژگی خاص دارد.
  • هرچه بیشتر منطق را در type system مدل کنید، کمتر نیاز به تست دستی برای حالت‌های edge case دارید — چون کامپایلر خودش جلوی نوشتن کد اشتباه را می‌گیرد.
