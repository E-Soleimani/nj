چرا یک فصل کامل دیگر برای OOP؟

در فصل ۱۰ با مبانی class، constructor، inheritance و private field در جاوااسکریپت آشنا شدیم. اما جاوااسکریپت خالص چند مفهوم مهم OOP (مثل Interface و Abstract Class) را ندارد — این‌ها فقط در TypeScript معنا پیدا می‌کنند. چون این مفاهیم پایه NestJS و پروژه‌های حرفه‌ای Node.js هستند، در این فصل همه را از صفر و به‌صورت کامل، ساده و روان مرور می‌کنیم.

چهار اصل OOP — یادآوری سریع و ساده

پیش از ورود به syntax، این چهار اصل را با مثال‌های خیلی ساده مرور می‌کنیم:

Encapsulation (کپسوله‌سازی)

پنهان کردن جزئیات داخلی — مثل ریموت کنترل تلویزیون: شما فقط دکمه را می‌زنید، نمی‌دانید داخلش چه اتفاقی می‌افتد.

Inheritance (وراثت)

یک کلاس ویژگی‌های کلاس دیگر را به ارث می‌برد — مثل فرزندی که رفتار پایه‌ای از والدینش می‌گیرد.

Polymorphism (چندریختی)

یک اسم متد، رفتار متفاوت در کلاس‌های مختلف — مثل دکمه «پخش» که در تلویزیون و پخش‌کننده موزیک کار متفاوتی می‌کند.

Abstraction (انتزاع)

نشان دادن فقط چیزهای ضروری — مثل رانندگی ماشین: فقط فرمان و پدال را می‌شناسید، نه موتور داخلش را.

Class و Constructor — یادآوری پایه

class-basics.ts
class Animal { // property ها — چیزهایی که هر Animal دارد name: string; age: number; // constructor — وقتی new Animal() صدا زده می‌شود، این تابع اجرا می‌شود constructor(name: string, age: number) { this.name = name; this.age = age; } // method — کاری که هر Animal می‌تواند انجام دهد makeSound(): string { return 'صدای نامشخص'; } describe(): string { return `${this.name}، ${this.age} ساله`; } } // instance — یک نمونه واقعی از کلاس Animal const myPet = new Animal('ببر', 3); console.log(myPet.describe()); // "ببر، 3 ساله"

تشبیه ساده: Class مثل نقشه یک ساختمان است — فقط طرح روی کاغذ. Instance (با new ساخته می‌شود) خود ساختمان واقعی است که از روی آن نقشه ساخته شده. از یک نقشه می‌توانید چندین ساختمان (instance) بسازید.

extends — وراثت بین کلاس‌ها

extends یعنی یک کلاس، همه چیزهای کلاس دیگر را می‌گیرد و می‌تواند چیز جدید هم اضافه کند یا رفتار قبلی را تغییر دهد. کلاس اصلی را Parent/Base/Super و کلاس جدید را Child/Derived/Sub می‌نامند.

extends-basics.ts
class Animal { constructor(public name: string) {} // این خط کوتاه‌شده همان this.name = name است makeSound(): string { return 'صدای نامشخص'; } } // Dog از Animal ارث می‌برد — پس Dog همه چیز Animal را دارد class Dog extends Animal { constructor(name: string, public breed: string) { super(name); // حتماً باید اول super() صدا زده شود — constructor والد را اجرا می‌کند } // override — بازنویسی متد makeSound که از Animal آمده makeSound(): string { return 'واق واق!'; } // متد جدید که فقط Dog دارد، Animal ندارد fetch(): string { return `${this.name} توپ را آورد`; } } const myDog = new Dog('رکس', 'ژرمن شپرد'); console.log(myDog.makeSound()); // "واق واق!" — نسخه Dog اجرا شد، نه Animal console.log(myDog.fetch()); // "رکس توپ را آورد" console.log(myDog instanceof Animal); // true — Dog در واقع یک Animal هم هست
⚠️

قانون طلایی super(): اگر constructor در کلاس فرزند تعریف کرده باشید، باید همیشه اولین خطش super(...) باشد — قبل از استفاده از this. بدون این، جاوااسکریپت خطا می‌دهد چون هنوز this ساخته نشده.

Access Modifiers — کنترل دسترسی به property و متد

Access Modifier مشخص می‌کند یک property یا متد از کجا قابل دسترسی است — این همان اصل Encapsulation است که در ابتدای فصل دیدیم، ولی حالا با syntax واقعی. TypeScript چهار سطح دسترسی دارد:

public (پیش‌فرض)

از همه‌جا قابل دسترسی — داخل کلاس، فرزندان، و بیرون از کلاس. اگر چیزی ننویسید، همین است.

private

فقط داخل همان کلاس قابل دسترسی — حتی کلاس فرزند هم نمی‌تواند مستقیم به آن دسترسی داشته باشد.

protected

داخل کلاس و همه کلاس‌های فرزند قابل دسترسی — ولی از بیرون (خارج از خانواده کلاس) قابل دسترسی نیست.

readonly

فقط یک بار (در constructor) قابل مقداردهی — بعد از آن دیگر قابل تغییر نیست.

access-modifiers.ts
class BankAccount { public owner: string; // همه‌جا قابل دسترسی (پیش‌فرض هم همین است) private balance: number; // فقط داخل خود این کلاس protected accountType: string; // داخل این کلاس و فرزندانش readonly accountNumber: string; // فقط یک بار مقداردهی می‌شود constructor(owner: string, initialBalance: number) { this.owner = owner; this.balance = initialBalance; this.accountType = 'عادی'; this.accountNumber = `ACC-${Date.now()}`; } // یک متد public که به balance خصوصی دسترسی امن می‌دهد getBalance(): number { return this.balance; // از داخل خود کلاس، دسترسی به private آزاد است } deposit(amount: number): void { if (amount <= 0) throw new Error('مبلغ باید مثبت باشد'); this.balance += amount; } } const account = new BankAccount('Ali', 1000); console.log(account.owner); // ✅ درست — public است console.log(account.getBalance()); // ✅ درست — از طریق متد public // account.balance; // ❌ خطای کامپایل — private است، از بیرون در دسترس نیست // account.accountNumber = 'X'; // ❌ خطای کامپایل — readonly است، تغییر ممکن نیست

protected در عمل — تفاوت با private

protected-vs-private.ts
class Employee { protected salary: number; // فرزندان می‌توانند ببینند، بیرون نه private ssn: string; // حتی فرزندان هم نمی‌توانند مستقیم ببینند constructor(salary: number, ssn: string) { this.salary = salary; this.ssn = ssn; } } class Manager extends Employee { giveRaise(amount: number) { this.salary += amount; // ✅ درست — protected از فرزند قابل دسترسی است // this.ssn; // ❌ خطا — private حتی از فرزند هم در دسترس نیست } } const manager = new Manager(50000, '123-45-6789'); // manager.salary; // ❌ خطا — از بیرون کلاس (حتی فرزند) به protected دسترسی نیست

میان‌بر رایج — تعریف Access Modifier مستقیم در Constructor

یکی از ویژگی‌های محبوب TypeScript این است که می‌توانید access modifier را مستقیم پشت پارامتر constructor بنویسید — این هم property را تعریف می‌کند هم مقداردهی می‌کند، در یک خط:

constructor-shorthand.ts
// ❌ روش طولانی — تعریف جدا + مقداردهی جدا class Product { private name: string; private price: number; constructor(name: string, price: number) { this.name = name; this.price = price; } } // ✅ روش کوتاه — یک خط برای هر پارامتر، همه چیز خودکار class Product { constructor( private name: string, private price: number, public readonly sku: string // می‌توانید چند modifier را با هم ترکیب کنید ) {} // همین! TypeScript خودش property و مقداردهی را می‌سازد } // این دقیقاً همان چیزی است که در فصل NestJS (23 و 63) همه‌جا دیدیم: // constructor(private usersService: UsersService) {}
⚠️

نکته مهم: این access modifier ها فقط در زمان کامپایل TypeScript چک می‌شوند. بعد از تبدیل به جاوااسکریپت خام، هیچ private/protected واقعی وجود ندارد — با کمی تلاش (مثل (obj as any).balance) هنوز می‌توان به آن‌ها دسترسی داشت. برای private واقعی که حتی در runtime هم محافظت‌شده باشد، باید از #privateField جاوااسکریپت (که در فصل ۱۰ دیدیم) استفاده کرد.

Interface — قرارداد شکل داده

Interface فقط در TypeScript وجود دارد (در جاوااسکریپت خالص نیست). Interface می‌گوید «هر چیزی که از این نوع باشد، باید این ویژگی‌ها و متدها را داشته باشد» — ولی خودش هیچ کد اجرایی ندارد، فقط یک قرارداد (contract) است.

interface-basics.ts
// تعریف یک interface — فقط شکل را مشخص می‌کند، هیچ پیاده‌سازی ندارد interface Flyable { maxAltitude: number; // property الزامی fly(): string; // متدی که هر پیاده‌کننده باید داشته باشد } interface Swimmable { maxDepth: number; swim(): string; } // یک interface می‌تواند شکل کامل یک object هم باشد interface User { id: string; name: string; email: string; age?: number; // ? یعنی اختیاری است } // استفاده ساده — هر object که این شکل را داشته باشد، معتبر است function printUser(user: User) { console.log(`${user.name} (${user.email})`); } printUser({ id: '1', name: 'Ali', email: 'ali@test.com' }); // درست — age اختیاری بود

تشبیه ساده: Interface مثل یک فرم استخدامی است که می‌گوید «هر متقاضی باید نام، سن، و مدرک تحصیلی داشته باشد» — خودش کسی را استخدام نمی‌کند، فقط شرایط لازم را مشخص می‌کند. هر کسی که این شرایط را داشته باشد، «واجد شرایط» است.

implements — پیاده‌سازی یک Interface

وقتی یک کلاس implements یک interface را دارد، یعنی متعهد می‌شود همه چیزهایی که در آن interface تعریف شده را واقعاً پیاده‌سازی کند. اگر چیزی کم باشد، TypeScript خطا می‌دهد.

implements-basics.ts
interface Flyable { maxAltitude: number; fly(): string; } // Bird متعهد می‌شود همه چیزهای Flyable را داشته باشد class Bird implements Flyable { maxAltitude = 3000; // اجباری — چون در Flyable تعریف شده بود fly(): string { // اجباری — چون در Flyable تعریف شده بود return 'پرنده در حال پرواز'; } } // یک کلاس می‌تواند چند interface را همزمان implement کند class Duck implements Flyable, Swimmable { maxAltitude = 500; maxDepth = 2; fly(): string { return 'اردک در حال پرواز'; } swim(): string { return 'اردک در حال شنا'; } } // ❌ اگر یک متد را فراموش کنید، TypeScript همان لحظه خطا می‌دهد: // class Penguin implements Flyable { // maxAltitude = 0; // // Error: Property 'fly' is missing // }

تفاوت extends و implements — سوالی که همیشه گیج‌کننده است

extends

ارث بردن کد واقعی از یک کلاس — property ها و متدها با پیاده‌سازی کامل منتقل می‌شوند. فقط از یک کلاس (single inheritance).

implements

متعهد شدن به یک قرارداد شکل — خودتان باید همه چیز را از صفر بنویسید. می‌توانید چند interface را همزمان implement کنید.

Abstract Class — نیمه‌کاره و اجباری

Abstract Class ترکیبی از class معمولی و interface است — می‌تواند هم متد با پیاده‌سازی کامل داشته باشد (مثل class عادی)، هم متد abstract بدون پیاده‌سازی که کلاس‌های فرزند مجبورند خودشان بنویسند. مهم‌ترین تفاوت با interface: نمی‌توانید مستقیم از یک Abstract Class نمونه (instance) بسازید.

abstract-class.ts
abstract class Shape { constructor(public color: string) {} // متد معمولی با پیاده‌سازی کامل — همه فرزندان همین را استفاده می‌کنند describe(): string { return `یک شکل ${this.color} با مساحت ${this.calculateArea()}`; } // متد abstract — فقط امضا دارد، بدون بدنه. هر فرزند مجبور است خودش بنویسد abstract calculateArea(): number; } // ❌ خطا — نمی‌توانید مستقیم از abstract class نمونه بسازید: // const s = new Shape('red'); // Error! class Circle extends Shape { constructor(color: string, private radius: number) { super(color); } // اجباری — چون Shape این متد را abstract تعریف کرده بود calculateArea(): number { return Math.PI * this.radius ** 2; } } class Rectangle extends Shape { constructor(color: string, private width: number, private height: number) { super(color); } calculateArea(): number { return this.width * this.height; } } const circle = new Circle('قرمز', 5); console.log(circle.describe()); // از متد مشترک Shape استفاده می‌کند، ولی calculateArea مخصوص Circle است

Interface یا Abstract Class؟ — تصمیم عملی

💡

اگر فقط می‌خواهید شکل را مشخص کنید و هیچ کد مشترکی بین پیاده‌کننده‌ها نیست، از Interface استفاده کنید. اگر می‌خواهید هم شکل را مشخص کنید هم مقداری کد مشترک واقعی بین همه فرزندان به اشتراک بگذارید (مثل متد describe در مثال بالا)، از Abstract Class استفاده کنید.

Polymorphism — چندریختی در عمل

Polymorphism یعنی می‌توانید با یک کد واحد، با چند نوع مختلف کار کنید — چون همه آن‌ها یک قرارداد مشترک (interface یا کلاس والد مشترک) دارند. این یکی از قدرتمندترین ابزارهای OOP است.

polymorphism-example.ts
// همان Shape انتزاعی از بالا را ادامه می‌دهیم // این تابع نمی‌داند نوع دقیق شکل چیست — فقط می‌داند یک Shape است function printTotalArea(shapes: Shape[]): void { let total = 0; for (const shape of shapes) { // polymorphism اینجاست: calculateArea() برای هر شکل رفتار متفاوتی دارد // ولی کد فراخوانی‌کننده اصلاً لازم نیست بداند کدام است total += shape.calculateArea(); } console.log(`مجموع مساحت: ${total}`); } const shapes: Shape[] = [ new Circle('قرمز', 5), new Rectangle('آبی', 4, 6), new Circle('سبز', 2), ]; printTotalArea(shapes); // هر عضو آرایه calculateArea مخصوص خودش را اجرا می‌کند

مثال دنیای واقعی در Node.js: در فصل Resilience Patterns، همه استراتژی‌های retry یک متد execute() مشترک داشتند. در فصل GoF Design Patterns، الگوی Strategy دقیقاً همین اصل Polymorphism بود — کد اصلی نمی‌داند کدام strategy اجرا می‌شود، فقط می‌داند یک متد مشترک صدا می‌زند.

جمع‌بندی: چهار کلمه کلیدی کنار هم

all-together.ts
// Interface — قرارداد interface PaymentMethod { process(amount: number): boolean; } // Abstract Class — نیمه‌کاره، کد مشترک + بخش اجباری abstract class BasePayment implements PaymentMethod { protected logs: string[] = []; // abstract — هر فرزند باید خودش بنویسد abstract process(amount: number): boolean; // متد مشترک با پیاده‌سازی — همه فرزندان استفاده می‌کنند log(message: string) { this.logs.push(message); } } // extends — ارث‌بری از BasePayment class CreditCardPayment extends BasePayment { process(amount: number): boolean { this.log(`پرداخت ${amount} با کارت اعتباری`); return true; } } class CryptoPayment extends BasePayment { process(amount: number): boolean { this.log(`پرداخت ${amount} با رمزارز`); return true; } } // Polymorphism — یک آرایه از انواع مختلف، همه با یک رابط مشترک const methods: PaymentMethod[] = [new CreditCardPayment(), new CryptoPayment()]; methods.forEach(m => m.process(100));

Decorators — تزیین کردن Class و Method

Decorator یک تابع خاص است که با علامت @ روی یک class، method، property یا parameter گذاشته می‌شود تا رفتار یا metadata اضافه کند — بدون اینکه کد اصلی آن قسمت را تغییر دهید. این دقیقاً همان چیزی است که NestJS (فصل ۲۳ و ۶۳) در همه‌جا از آن استفاده می‌کند: @Controller، @Injectable، @Get و غیره.

تشبیه ساده: Decorator مثل یک برچسب روی یک بسته پستی است. خود بسته (کلاس یا متد) تغییر نمی‌کند، ولی برچسب («شکستنی»، «فوری») به سیستم پستی (framework) می‌گوید با این بسته چطور رفتار کند.

فعال کردن Decorators در TypeScript

tsconfig.json
{ "compilerOptions": { "experimentalDecorators": true, "emitDecoratorMetadata": true } }

Class Decorator — تزیین کل کلاس

class-decorator.ts
// یک Class Decorator ساده — constructor کلاس را می‌گیرد function Loggable(constructor: Function) { console.log(`کلاس ${constructor.name} ساخته شد`); } @Loggable class UserService { getUser() { return 'Ali'; } } // خروجی موقع import شدن فایل: "کلاس UserService ساخته شد" // Decorator Factory — تابعی که یک decorator برمی‌گرداند (پارامتر می‌پذیرد) function Component(name: string) { return function(constructor: Function) { constructor.prototype.componentName = name; }; } @Component('user-widget') // دقیقاً همین الگو در @Controller('users') در NestJS استفاده می‌شود class UserWidget {}

Method Decorator — تزیین یک متد

method-decorator.ts
// اندازه‌گیری زمان اجرای یک متد — کاربرد واقعی و رایج function MeasureTime(target: any, propertyKey: string, descriptor: PropertyDescriptor) { const originalMethod = descriptor.value; // متد اصلی را نگه می‌داریم // متد اصلی را با یک نسخه جدید جایگزین می‌کنیم descriptor.value = function(...args: any[]) { const start = Date.now(); const result = originalMethod.apply(this, args); // متد اصلی را صدا می‌زنیم console.log(`${propertyKey} در ${Date.now() - start}ms اجرا شد`); return result; }; } class ReportService { @MeasureTime generateReport() { // یک کار سنگین فرضی for (let i = 0; i < 1000000; i++) {} return 'گزارش آماده شد'; } } new ReportService().generateReport(); // خروجی: "generateReport در 3ms اجرا شد"

// Property Decorator — روی یک property اجرا می‌شود function Required(target: any, propertyKey: string) { console.log(`${propertyKey} الزامی علامت‌گذاری شد`); // در پیاده‌سازی واقعی، معمولاً metadata ذخیره می‌شود // که بعداً یک validator آن را می‌خواند (دقیقاً کاری که class-validator در فصل 27 و 45 می‌کند) } class CreateUserDto { @Required name: string; @Required email: string; } // Parameter Decorator — روی یک پارامتر تابع اجرا می‌شود // دقیقاً معادل چیزی که @Param() و @Body() در NestJS پشت صحنه انجام می‌دهند (فصل 23 و 63) function LogParam(target: any, methodName: string, parameterIndex: number) { console.log(`پارامتر شماره ${parameterIndex} در متد ${methodName} رصد می‌شود`); } class OrderController { createOrder(@LogParam userId: string) { /* ... */ } }

چرا NestJS این‌قدر روی Decorator تکیه دارد؟

اکنون که مکانیزم Decorator را دیدید، الگوهایی که در فصل ۲۳ و ۶۳ استفاده کردیم منطقی‌تر می‌شوند:

nestjs-decorators-explained.ts
@Controller('users') // Class Decorator با factory — مشخص می‌کند این کلاس یک HTTP controller است export class UsersController { @Get(':id') // Method Decorator — این متد به GET /users/:id پاسخ می‌دهد getUser( @Param('id') id: string // Parameter Decorator — این پارامتر از URL params می‌آید ) { return this.usersService.findOne(id); } } // پشت صحنه، NestJS دقیقاً همان مکانیزمی که بالا دیدیم را استفاده می‌کند: // این metadata‌ها را می‌خواند و بر اساس آن‌ها route، injection، و validation را می‌سازد

نکات کلیدی برای مصاحبه

  • extends: ارث بردن کد واقعی از یک کلاس — فقط از یک کلاس ممکن است (single inheritance).
  • implements: تعهد به یک قرارداد شکل (interface) — می‌توانید چند interface را همزمان implement کنید.
  • public/private/protected/readonly: چهار سطح دسترسی TypeScript — public همه‌جا، private فقط داخل همان کلاس، protected داخل کلاس و فرزندانش، readonly فقط یک‌بار قابل مقداردهی.
  • میان‌بر constructor shorthand (مثل constructor(private name: string)) هم property می‌سازد هم مقداردهی می‌کند — همان الگویی که در تزریق dependency در NestJS همه‌جا دیدیم.
  • interface هیچ کد اجرایی ندارد، فقط شکل را تعریف می‌کند؛ در runtime هم اصلاً وجود ندارد (فقط زمان کامپایل چک می‌شود).
  • abstract class ترکیبی از interface و کلاس معمولی است — می‌تواند هم متد پیاده‌سازی‌شده هم متد اجباری (abstract) داشته باشد؛ نمی‌توان مستقیم از آن instance ساخت.
  • Polymorphism یعنی یک قطعه کد می‌تواند با چند نوع مختلف کار کند، چون همه یک قرارداد مشترک دارند — پایه الگوی Strategy در فصل GoF.
  • سوال رایج: «چرا نمی‌توان از abstract class مستقیم instance ساخت؟» — چون ممکن است متد abstract بدون پیاده‌سازی داشته باشد؛ اگر instance مستقیم مجاز بود، صدا زدن آن متد خطای runtime می‌داد؛ TypeScript این را از قبل، در کامپایل، جلوگیری می‌کند.
  • سوال رایج: «فرق private در TypeScript و #field در جاوااسکریپت چیست؟» — private فقط زمان کامپایل چک می‌شود و بعد از تبدیل به JS خام از بین می‌رود (با ترفند قابل دور زدن است)؛ #field یک ویژگی واقعی زبان جاوااسکریپت است که حتی در runtime هم واقعاً غیرقابل دسترسی از بیرون است.
  • یک تله رایج: قاطی کردن interface و type در TypeScript — هر دو برای تعریف شکل استفاده می‌شوند، ولی interface قابل extend/merge شدن است و برای کلاس‌ها با implements طبیعی‌تر است؛ type برای union و ترکیب‌های پیچیده‌تر بهتر است (یادآوری فصل ۱۲).
  • یک تله رایج دیگر: فراموش کردن اینکه protected از «بیرون» کلاس (حتی توسط یک instance از همان کلاس در یک متد دیگر) قابل دسترسی نیست — فقط از داخل خود کلاس یا کلاس‌های فرزند در زمینه this قابل استفاده است.
  • Decorator تابعی است که metadata یا رفتار اضافه به class/method/property/parameter می‌دهد، بدون تغییر کد اصلی آن — پایه معماری NestJS.
  • چهار نوع Decorator: Class (روی کل کلاس)، Method (روی یک متد، با دسترسی به descriptor)، Property (روی یک ویژگی)، Parameter (روی یک پارامتر تابع).
  • سوال رایج: «چطور @Controller در NestJS کار می‌کند؟» — یک Class Decorator (در واقع Decorator Factory چون آرگومان می‌گیرد) است که metadata (مثل مسیر پایه route) را روی کلاس ذخیره می‌کند؛ NestJS در زمان راه‌اندازی این metadata را می‌خواند و route‌ها را می‌سازد.
